BP HTML Report — Enhancement Plan

Covers scripts/bp_html_report_v3.py (primary target — handles release files) · Pass 1 (Enhancements 1–5) shipped and reviewed · Pass 2 (verified bug fixes + Enhancements 6–8) planned below, pending approval

Scope & Script selection

bp_html_report_v3.py is the authoritative script — it handles .bprelease, .bpprocess, and .bpobject via the _detect_file_type() guard and calls generate_release() for releases. All enhancements target this file.

bp_report_v3.py generates Markdown, not HTML. Its file-size issue (1.5 MB .md) is addressed separately in Enhancement 4 (reachability pruning), which applies to both scripts since they share the same parsed data dict from bp_parser_v2.py / bp_release_parser.py.

bp_graph_v3.py is the source of the per-page PNG graphs currently embedded as inline base64 — this is the single biggest contributor to the 40–70 MB HTML size.

All scripts/ files are standalone helper utilities — parsing and report generation — sitting entirely outside src/flowsmith and exempt from its package-level rules (typer-only CLI, 85% coverage, etc.). These enhancements deliberately make the same generated output serve two audiences at once: a human reviewing the HTML report, and a downstream tool or LLM ingesting the data/ exports (JSON/JSONL/pruned Markdown).

JSON serialisation — sets aren't native to release_result, but the new reachability code introduces them

Verified: parse_release()'s return dict (bp_release_parser.py lines 233–241) is plain dicts/lists/strings/ints — no sets today. The risk is new, not existing: _reachable_vbo_actions() in Enhancement 4 returns dict[str, set[str]] by design, and scripts/bp_common.py is the single place both the HTML renderer and the data/ JSON exporter pull from. If that set-valued structure gets attached to an artifact dict before it reaches json.dump(), serialisation breaks.

Fix: a shared _json_default(o) helper in scripts/bp_common.py (sorted(o) if isinstance(o, set) else str(o)) passed as default= to every json.dump() call in Enhancement 3 — one line at each call site, not a pre-walk pass over the whole tree.

Reachability pruning — remove uncalled VBO actions

New logic shared utility + both report scripts

The problem precisely

A VBO object (e.g. Utility - File Management) may have 60 action pages. A process might call only 4 of them (Get Files, Read Text File, Write Text File, File Exists). The current scripts render all 60 pages in the VBO section — 93% of the output is dead weight.

Existing hook — already there

The parser already records, on every Action stage: vbo_object (the VBO name) and vbo_action (the specific action called). generate_release()'s VBO cross-reference section already computes an equivalent vbo_calls: dict[str, set] per process — but only as a local, render-time variable (bp_html_report_v3.py lines 958–962), never stored back into release_result. That's why data/release.json is safe to dump as-is today; it's the new _reachable_vbo_actions() output below that introduces sets into anything meant for JSON export (see the serialisation note in Enhancement 3).

Algorithm: build reachable_actions set before rendering 

# In generate_release() / generate_split(), before rendering objects:

def _reachable_vbo_actions(procs: list[dict]) -> dict[str, set[str]]:
    """
    Returns {vbo_name: {action_name, …}} for every VBO action
    actually called from any process in this release.
    """
    called: dict[str, set] = {}
    for proc in procs:
        for stage in proc["stages"]:
            vbo = stage.get("vbo_object")
            action = stage.get("vbo_action")
            if vbo and action:
                called.setdefault(vbo, set()).add(action)
    return called

When rendering a VBO object's pages, only include a page if page["name"] in reachable_actions.get(vbo_name, set()). Unreachable pages are counted in a footer note: "47 unreachable action pages omitted — use --include-all to show them."

Reachability for process pages

_full_traversal() does not currently expose reachability as a flag — it returns one merged list: BFS-reached stages first, then orphaned stages appended at the end, with no per-stage marker distinguishing the two groups (verified against bp_html_report_v3.py lines 83–115). Getting is_reachable: bool onto each stage/page requires a small but real change: either return the internal seen set alongside the merged list, or add a sibling helper _reachable_stage_ids(page_id, stages, stage_by_id) -> set[str] that both the existing renderer and the new pruning pass call. Treat this as its own sub-task, not a free read of existing state.

  • A process page is reachable if it has at least one reachable non-Data/Block stage.
  • Pages that are only Data/Block stages (no Start→End flow) are always rendered as a compact data-items-only table — no graph, no stage cards — never hidden and never expanded to a full page section. A reviewer documenting data items across a VBO still needs to see them; this is the fixed default behaviour, not a configurable option.

Shared module — avoid duplicating the algorithm

New file scripts/bp_common.py holds _reachable_vbo_actions() and _reachable_stage_ids() as the single source of truth. Both bp_html_report_v3.py and bp_report_v3.py import from it rather than each carrying their own copy — otherwise the two report generators can silently drift on what "reachable" means, since today they already duplicate generate_release()-style logic independently.

CLI flag

--include-all      # disable pruning — render every page of every VBO (old behaviour)
# default: pruning ON

CSS class extraction — eliminate repeated inline styles

Refactor bp_html_report_v3.py

Current problem

Every call to _stage_card(), _render_stage_detail(), _section_header(), and _artifact_card() emits full inline style="…" attribute strings. With 500+ stages, strings like style="padding:4px 10px 4px 0;font-size:12px;word-break:break-all" are repeated hundreds of times — adding ~200–400 KB of redundant text.

Fix: move all repeated styles to styles.css as named classes

  • Extract a named class for every distinct style pattern used more than ~5 times.
  • Key candidates: .stage-card, .stage-summary, .detail-row, .detail-label, .detail-val, .section-sep, .badge, .dot.
  • Dynamic values (colours per stage type) stay inline — only the structural/layout rules are extracted.

Estimated gain

~200–400 KB reduction in the HTML portion itself, on top of the much larger gains from Enhancements 1 and 4.

Testing strategy — kept isolated from the flowsmith suite

New scripts/tests/

scripts/ is standalone tooling outside src/flowsmith and not bound by the package's 85% coverage mandate. Given the size of this refactor, targeted tests are still worth adding for the riskiest new pieces — reachability pruning, the split-output writer, manifest correctness — not full coverage, and they must never run as part of the flowsmith suite.

Isolation mechanism

  • Tests live in scripts/tests/ — a sibling to scripts/, outside tests/.
  • pyproject.toml already scopes pytest via testpaths = ["tests"], so bare uv run pytest and uv run pytest tests/ -v never discover scripts/tests/ — no markers or opt-outs needed.
  • scripts/tests/pytest.ini — a local, minimal config (no --cov=flowsmith, no fail_under=85) so a scripts-only run doesn't fail on flowsmith coverage it never touches. Pytest's config discovery finds this file before walking up to the root pyproject.toml.
  • Run explicitly and separately: uv run pytest scripts/tests/ -v — never folded into the flowsmith --cov invocation.

Fixtures — inline conftest.py factory, not a static JSON file

scripts/tests/conftest.py exposes a factory fixture (e.g. make_release_result(processes=…, vbos=…)) that builds a minimal synthetic release_result in Python — 1 process + 1 VBO with 2 action pages, only 1 called, is the base case for _reachable_vbo_actions() and the split-output writer. A factory beats a hand-maintained JSON blob here: it stays readable as assertions change, and tests never depend on a real .bprelease sample file being present on disk.

Pass 1 review — verified bugs (fix in Pass 2)

Found by tracing each of the review's four flagged symptoms back to the exact line in the shipped output and the code that produced it — not by inspection alone.

1. VBO reachability pruning never fires — two stacked bugs

Bug 1 — wrong type string. The pruning check in bp_html_report_v3.py (~line 1434) compares page.get("type") == "Action", but real parsed page type values are "implicit", "CleanUp", and "Normal" (verified against data/utility-file-management.json) — never "Action". The condition never matches, so pruned_pages stays empty for every VBO, every run.

Bug 2 — filter never reaches the body content. Even with Bug 1 fixed, _artifact_page_html()'s main content loop (~line 999) rebuilds page_sections by iterating every page unconditionally — it never consults the pruned_pages list it's handed. Only the image-write loop in generate_split() was ever wired to skip pruned pages; the stage-card HTML body was not. Both call sites need the fix together.

Evidence: the process calls only Delete File and File Exists on Utility - File Management, yet pages/utility-file-management.html renders all 33 pages / 33 images, including unused actions (Get Files, Write Text File, Move File, Copy File, …).

2. Expand/collapse-all — dead code on index.html

toggleAll() targets #pages-container details, #artifacts-container details. #pages-container doesn't exist anywhere in index.html's DOM, and #artifacts-container is a flat <ul><li><a> nav list with zero <details> elements inside it. The buttons always toggle an empty NodeList. Leftover from the old single-file template, where each artifact was a <details> accordion on the same page — that content moved to pages/*.html in the split refactor, but the JS/buttons weren't updated to match.

3. Search — selector mismatch with the new content model

doSearch() only scans summary, td elements. The artifact list — the primary thing a user would search for — is <li><a> markup with neither tag, so searching "Excel" cannot match the visible "MS Excel VBO" link. Only the env-vars/xref tables and the couple of stray <details> blocks are reachable by the current search.

4. CSS extraction (Enhancement 5) is half-done

The .stage-card/.page-card/.detail-table classes in styles.css are genuinely extracted and correctly used in pages/*.html. But index.html's nav list, header, and buttons remain 100% inline style="…" per element — the exact pattern Enhancement 5 was meant to eliminate, and a source of visual drift between index.html and pages/*.html over time.
