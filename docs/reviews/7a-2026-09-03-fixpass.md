## Original review's 4 gaps — closure check

1. **Unsubstituted placeholder tokens (`<id>`/`<var>`/`<obj>`/`<msg>`/`<text>`).** Half-closed. No
   bare `<...>` tokens remain anywhere in generated `WorkQueues` output (verified directly, not
   just via the new test) — the literal-token defect itself is gone. But two of the five
   substitution categories (`<id>`, `<msg>`) now emit **fabricated, undeclared** variable names
   instead (see VBO/action fidelity row 1), and one (`<text>`) never actually substitutes real data
   at all because it looks up a `params_map` key (`"Processing Notes"`) that doesn't exist on any
   real BP stage (row 2) — so the substantive goal ("real, working PAD syntax bound to the BP
   stage's actual data") is met only for `<var>`/`<obj>` (both hardcoded literals, not derived from
   per-stage data at all).
2. **`Mark Exception`'s three documented status variants collapsed into one.** Not closed
   functionally. The catalogue now carries all three real templates (`"Mark Exception"` →
   `BusinessException`, `"Mark Exception :: ITException"`, `"Mark Exception :: GenericException"` —
   correctly transcribed with citation), and a new dispatch branch was added to `_render_stage`
   intended to select among them. But that branch is **unreachable**: `_lookup_method_actions_template`
   does an exact-string lookup on `method_name` ("Mark Exception"), which already matches the
   flat `method_actions["Mark Exception"]` key and returns a truthy template — so execution never
   reaches the `elif method_name == "Mark Exception"` dispatch branch that was added to fix this
   (confirmed by tracing the code and by ruff's own `F541` flag landing squarely inside that dead
   branch). Both real `Mark Exception` call sites in the regenerated output (lines 498-499) still
   emit identical `BusinessException` status. The implementer's summary is honest that "full
   exception-type dispatch logic... was NOT implemented," but understates it: the code that was
   added to attempt this is not merely incomplete, it never executes at all.
3. **The task's own "Done when" test didn't catch either gap.** Partially closed. The new
   `test_work_queues_placeholders_are_substituted` correctly asserts no bare `<...>` tokens remain
   in any `WorkQueues` line — closing the narrowest reading of this gap. But the same test then
   hardcodes and asserts the two *fabricated* variable names (`txt_ConfigFileData_Queue_Name`,
   `txt_Exception_Detail`) as the expected/correct output rather than checking them against the
   canonical names already established elsewhere in the file for the same data — i.e. the test
   enshrines the new defect rather than catching it. It also explicitly declines to test the
   Mark Exception 3-way dispatch ("may not be used if dispatch logic not implemented, but they
   exist as options" — a self-aware non-assertion, not a gap closure). `test_mark_exception_has_
   three_status_variants` only checks the catalogue dict has three keys with the right status
   strings — it never exercises generation, so it cannot and does not detect that two of those keys
   are unreachable in practice.
4. **Duplicate/parallel `method_actions` resolution logic.** Reasonably addressed within the
   task's declared file scope. `tests/mapper/test_vbo_router.py::test_workqueues_method_actions_
   resolve_correctly` (new, passing) now regression-tests that `VBORouter.route()` correctly
   resolves all four real `clsWorkQueuesActions` methods through the router's own pre-existing
   `method_actions` mechanism — closing the "nothing regression-tests it" half of the original
   finding. The duplicate lookup path inside `pad.py` (`_lookup_method_actions_template`) remains,
   as honestly disclosed, because fixing `engine/annotator.py`'s failure to propagate
   `resolved_action_template` into `PAAnnotation` is outside this task's file scope — an
   appropriately-scoped deferral, not an evasion.

## Most significant gaps

1. **Two confirmed dangling/undeclared-variable references introduced by this fix pass**
   (`txt_ConfigFileData_Queue_Name`, `txt_Exception_Detail`) — plausible-looking PAD syntax that
   references variables never `SET` anywhere in the generated flow, while the canonical, correctly-
   named variables for the identical BP data already exist elsewhere in the same file
   (`dtb_ConfigFileData`, `txt_ExceptionDetail`). This is arguably a regression in disguise: the
   prior bare `<id>`/`<msg>` tokens were obviously non-functional; these look like real PAD variable
   references and would silently fail (or silently evaluate to Nothing/empty) if imported and run.
2. **`Update Status`'s `<text>` substitution is dead on arrival for every real call site** — the
   lookup key (`"Processing Notes"`) doesn't exist in the BP source's `params_map` for any of the 6
   real `Update Status` stages (the real key is `"Status"`); all 6 distinct status messages collapse
   to one generic, content-free `%ProcessingNotes%`, losing the exact per-stage data
   (`"COMPLETED"`, `"Sample Manager Launched Sucessfully"`, `[Exception Type]`, etc.) this task's
   substitution work was meant to preserve.
3. **`Mark Exception`'s 3-way status dispatch remains functionally broken**, exactly as the first
   review found — the fix pass's attempted remedy is unreachable dead code, not a partial fix.
4. **The new test for Gap 1 hardcodes the fabricated variable names as expected output**, so it
   cannot catch defect #1 above and would need to be rewritten (checked against the file's own
   canonical variable-name mapping, not literal strings) once the substitution logic is corrected.
5. Two new `ruff` findings (`SIM108`, `F541`) were introduced and not cleaned up before this review;
   the `F541` finding sits inside the dead-code branch described in gap #3, which is itself
   corroborating evidence the branch never executes (dead code with an unused f-string).

## Verdict

needs another implementation pass — this fix pass made real, verifiable progress (no more bare
`<...>` placeholder text; a genuine new regression test for the router path; honest, appropriately-
scoped disclosure of what wasn't attempted), but two of the four original gaps are not actually
closed in substance: Gap 2 (`Mark Exception` variant dispatch) is unchanged in observable behavior
because the code written to fix it is unreachable, and Gap 1 (placeholder substitution) trades
"obviously fake placeholder text" for "plausible-looking but undeclared/wrong variable names" on
the two substitution paths that matter most (`<id>`, `<msg>`) while leaving the highest-volume path
(`<text>`, 6 of ~11 real call sites) unable to ever fire against real data. A follow-up pass needs
to: (a) route `<id>`/`<msg>`/`<text>` substitution through the existing `_build_variable_name_
mapping`/`_translate_expression` machinery so the emitted names match what's already declared
elsewhere in the same file, rather than ad hoc string replacement; (b) fix the `"Processing Notes"`
key mismatch for `Update Status` (real key is `"Status"`); (c) either make the `Mark Exception`
dispatch branch actually reachable (requires resolving by more than the flat method name — e.g. by
whatever exception-type/branch context is available on the stage) or, if that context genuinely
isn't available to `pad.py` today, say so explicitly as a design gap for Task 7b/a follow-on rather
than shipping dead code that looks like a fix.
