## Headline finding

The implementer's "no deviations" claim is false, and the self-reported "Open Questions" list
undercuts it further than even the implementer stated. Verified directly against real generated
output for `PID_0171.bprelease`:

- **0 of 104** real `CALCULATION` stages produce a translated `SET` line. All 104 still emit
  either the literal placeholder `%SomeVar%` or an unrelated boilerplate value. Root cause: the
  new wiring code does `stage.params_map.get(stage.name, "")` (`pad.py:1064`), but the BP parser
  stores a Calculation's expression keyed by the **target variable name** (`<calculation
  stage="Consecutive Exception Count" expression="...">`), which is essentially never equal to
  the Calculation stage's own developer-assigned label (`stage.name`, e.g. `"Count"`). Confirmed
  by direct query against `ast.json`: `0/104` Calculation stages have `stage.name` present as a
  key in their own `params_map`.
- **0 IF statements** appear anywhere in the 1,172-line generated Performer `.robin` file. Root
  cause: `mapping/stage_rules.yaml`'s `DECISION` entry sets `pa_target_action` to the literal
  string `"IF <expr> THEN <true-branch> ELSE <false-branch> END"` (the template placeholder
  text itself), not `"Condition"` — so `pad.py`'s `elif target_type == "Condition":` branch
  (pre-existing, not part of this diff, but load-bearing for Do-step 2) never fires against any
  real annotated Decision stage. Confirmed against `ast.json`: **every** Decision stage's
  `pa_annotation.target_type` is that literal template string, including ones with rich real
  expressions the translator should have handled well, e.g. `Limit?` →
  `[Consecutive Exception Count]>=[Consecutive Exception Limit]` (§A7's own consecutive-exception
  logic) and `System Exception?` → `Lower([Exception Type])="system exception" OR ...`.
- **145 occurrences of the literal string `%SomeVar%`** remain in the real generated Performer
  `.robin` file.
- Excel/File/Folder/DateTime/Text/WorkQueues fallback values are **byte-identical to the
  pre-Task-5b placeholders** in real output (`$'''C:\path\to\file.xlsx'''`, `Sheet1`,
  `'C:\\path\\to\\file.txt'`, `'QueueName'`). Root cause: `_extract_param_from_stage` looks up
  lowercase single-word keys (`"filepath"`, `"sheet"`, `"ExcelInstance"`, `"queue"`, …) but real
  BP `<input name="...">` keys are the developer's actual parameter labels with spaces/casing
  (`"File name"`, `"Workbook Name"`, `"Worksheet Name"`, `"handle"` — confirmed directly from
  `ast.json`'s Excel-module stages). The lookup essentially never matches, so every module
  template falls through to its `or "<placeholder>"` fallback on the real corpus.
- WorkQueues module calls never even reach the new Task 5b wiring code at all in real output —
  they render as `# TODO: WorkQueues.<Action> — complete this action block` stub lines, meaning
  the whole `WorkQueues` branch added in this diff (`pad.py:1196-1209`) is dead code against
  `PID_0171.bprelease` (those stages are routed to the MANUAL-band stub path upstream before
  reaching this dispatch).

The two new unit tests pass only because they hand-construct synthetic stages that sidestep both
root causes: the Calculation test sets `stage.name = "txt_ExceptionType"` *and*
`stage.params_map = {"txt_ExceptionType": "..."}"` (making the key match, which never happens on
real data), and the Decision test manually sets `target_type="Condition"` on the `PAAnnotation`
(bypassing the real annotator/`stage_rules.yaml` path entirely, which never produces that
`target_type`). Both tests are true positives for the code they exercise but are not
representative of what the generator actually does against real BP input — which is exactly what
the coordinator asked me to check rather than accept at face value.

## Do-step-by-Do-step verification

1. **Do-step 1** (confirm the placeholders to replace) — done; the audit in the summary is accurate.
2. **Do-step 2** (Calculation expression → `SET` with §B10 point 3 translation, `Trim`/`Lower` →
   separate action lines) — the translation function itself (`_translate_bp_expression`) is
   written correctly in isolation (bracket-reference → bare var, `&` → `+`), but it is **not
   reachable on any real Calculation stage** (see above). The `Trim`/`Lower` → separate
   `Text.Trim`/`Text.ChangeCase` action-line requirement is explicitly left unimplemented — the
   code has a comment acknowledging it (`pad.py:1370-1376`) and the implementer's own summary
   calls it out as deferred. Matches the implementer's self-report on this specific point.
3. **Do-step 3** (VBO `method_actions` real-parameter substitution via `mapper/vbo_router.py`) —
   **not attempted at all**. `vbo_router.py` is never imported by `pad.py` (confirmed via grep);
   `RoutingDecision.resolved_action_template` (the field that would carry the real `method_actions`
   template) is not even carried through to `PAAnnotation` by the engine, so `pad.py` has no
   plumbing available to consume it even if it wanted to. This is an explicit, numbered Do-step,
   not a stretch goal, and it is entirely absent from the diff — confirmed, not just self-reported.
4. **Do-step 4** ("never silently drop" — TODO stub, not a placeholder that looks real) —
   **violated systematically**. Every module branch (Excel/Text/File/DateTime/Folder/WorkQueues)
   falls back to a hardcoded-looking literal (`'C:\\path\\to\\file.txt'`, `'QueueName'`,
   `'Sheet1'`, etc.) rather than a `# TODO` stub when `_extract_param_from_stage` returns `None` —
   which, as shown above, is effectively always on real data. This is precisely the anti-pattern
   Do-step 4 calls out by name ("don't emit a placeholder that *looks like* real code when it
   isn't").

## Most significant gaps

- **Do-step 3 skipped entirely** — no `vbo_router.py`/`method_actions` integration, despite being
  an explicit numbered Do-step. The implementer's summary at least reports this honestly as "not
  attempted," but frames the rest of the task as complete when the reason Do-step 3 was skipped
  (the PAAnnotation model doesn't even carry `resolved_action_template`) also undermines the
  other Do-steps' real-world reach.
- **The core wiring is miswired against real data, not just incomplete.** `SetVariable` looks up
  the BP calculation expression under the wrong dict key (`stage.name` instead of the actual
  target-variable key the parser uses), and `Condition` dispatches on a `target_type` string real
  Decision-stage annotations never produce. Both bugs are 100% reproducible against the real
  corpus (0/104 and 0/N respectively) — this is not an edge case, it's the general case.
- **The two new tests are false positives for real-world coverage.** Each was hand-built to make
  the broken lookup path succeed (matching `stage.name` to its own `params_map` key; hand-setting
  `target_type="Condition"` directly on the annotation) rather than exercising the real
  parser→annotator→generator pipeline the way `tests/e2e/test_pid171_pipeline.py` does. "64/64
  passed, 90% pad.py coverage" is true and uninformative about whether this task's actual goal was
  met.
- **Do-step 4's "never silently drop" rule is inverted for the generic module templates.** Every
  Excel/File/Folder/DateTime/Text/WorkQueues branch falls back to a placeholder that *looks like*
  real code (a plausible file path, sheet name, queue name) instead of an honest `# TODO` when
  no real parameter can be resolved — which is effectively always, since the lookup keys
  (`"filepath"`, `"sheet"`, `"ExcelInstance"`, `"queue"`, …) don't match real BP parameter names
  (`"File name"`, `"Worksheet Name"`, `"handle"`, …).
- **`SET <stage.name> TO ...` emits invalid Robin variable names.** For DATA/CALCULATION stages
  whose display name contains spaces (the common case — `"Exception Type"`, `"Loaded DateTime"`),
  the generated `SET` line's left-hand side is not a legal PAD variable token. Pre-existing before
  this diff for the un-prefixed name, but this task's own summary claims "Real Data Wiring" fixed
  this class of line, when the identifier problem is untouched.
