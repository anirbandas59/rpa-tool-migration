## Verification performed

### 1. Was expanding `build_ast()`'s signature scope creep?

**No — it was pre-assigned to this task, not implementer over-reach.** Task 3a's own "Out of
scope" text (`docs/pad-generation-task-prompts.md` lines 460-464) says verbatim: *"anything in
`ast/builder.py` that consumes this new multi-artefact shape (Task 4a) — this task only needs to
return the data, not wire it through the whole pipeline yet. If `ast/builder.py` breaks because it
expects the old single-artefact shape, that's expected and will be fixed in Task 4a."* Task 4a's
own step 4 requires a test against the real `PID_0171.bprelease` sample, which is impossible to
write at all without `build_ast()` first accepting the `MultiArtefactRelease` shape
`parse_process()` now returns. The `isinstance(raw, dict) and "processes" in raw` branch plus
`release["processes"][0]` extraction is the minimal shape needed to unblock this. One soft gap:
selecting `processes[0]` unconditionally (rather than by name/`is_main_process` marker) is fragile
in principle — it happens to be correct for this release only because `PID_171_US_Process_LIMS_Prelude`
is first in document order — but this is a reasonable, low-risk choice for the only consumer that
exists today, not a defect.

### 2. Is the "parser bug" real, and does it invalidate the real-sample test?

**Confirmed real, pre-existing (not introduced this session), and — more seriously than the
implementer's summary suggests — it is not the only defect breaking reachability for the real
sample; a second, independent, also-pre-existing bug compounds it.**

- **Bug A (parser/process.py, pre-existing since commit `40164dd`, long before this session):**
  the "find the main page" logic (`process.py` ~line 604-616) looks for a subsheet whose *name*
  equals the *process* name (never true in practice), then falls back to "the first subsheet in
  dict-iteration order" — which for PID_0171 happens to land on `Mark Item As Completed`, not the
  real Main Page. This silently merges the real no-`<subsheetid>` main-flow stages together with
  the *actual* `Mark Item As Completed` subsheet's own stages into one mislabelled page. Confirmed
  via `git log -p` that this exact logic dates to the original parser commit — not a regression
  from Task 1a/3a/3b this session.
- **Bug B (ast/builder.py, pre-existing since the very first AST-builder commit `fe614f0` —
  also predates this session):** `_SKIP_TYPES` includes `"Process"` alongside the genuinely
  skippable `Anchor`/`Note`/`SubSheetInfo`/`ProcessInfo` types. This directly contradicts
  CLAUDE.md's own documented normalisation table ("`PROCESS → ACTION (is_process_call=True)`").
  Verified: `is_process_call` does not exist anywhere in the codebase, and the parser never even
  captures `<processid>` (checked `process.py` directly — zero matches). Consequence, traced by
  hand: the real Main Page's genuine execution chain (`Start` → `Get User Name` → `Download Config
  File from SharePoint` [a `type="Process"` stage] → `ConvertConfigFile As Collection` → ... →
  `Get Next Item` → `Get Mails`/`Populate Queue` calls) is severed at the very first
  `Process`-type stage, three hops in, because that stage is dropped entirely — its own
  `onsuccess` edge is never even recorded as a `BPStage`, so the BFS queue has nothing to advance
  on. Traced this with an instrumented replica of `_compute_reachability`'s BFS: it terminates
  after exactly 3 steps, having visited only 1 of 23 pages.
- **Net effect, independently reproduced by running `build_ast(parse_process(PID_0171_path))`
  directly:** `Get Mails` = unreachable, `Populate Queue` = unreachable — both **fail** the task's
  own literal step-4 requirement — while `Mark leftout Items as Exception` and `Send Info to Data
  Gateways` also show unreachable, but **only because virtually every page in the process shows
  unreachable** (22 of 23), not because the algorithm is correctly distinguishing orphans from
  real call targets. This directly refutes the implementer's Open Questions claim that "Task 4a's
  reachability algorithm works correctly regardless of which page is marked as main" — it does
  not; fixing bug A alone would still leave bug B severing the chain, and vice versa.
- Both bugs are pre-existing and neither was introduced by this session's Task 1a/3a/3b work
  (confirmed via `git log -p --follow` on both files). Bug B, however, lives in `ast/builder.py`
  itself — a file squarely **inside Task 4a's own declared file scope** — and directly blocks the
  very `processid` cross-reference mechanism Task 4a's Do-step 1 explicitly asks for ("`SubSheet`/
  `Process`-type `ACTION` stages' `processid` cross-references to other pages"). This was not a
  problem the implementer merely inherited from elsewhere; a correct Task 4a pass needed to at
  least surface it as a blocking dependency, since it sits in the very file being edited.

### 4. Reachability algorithm soundness (code review)

- `onsuccess`/`ontrue`/`onfalse` traversal: mechanically correct BFS over `BPStage.onsuccess_target`
  etc. — no complaint with this part of the logic in isolation.
- SubSheet cross-reference: matched **by page name**, not by `processid` as the task's Do-step 1
  literally specifies. This is a reasonable workaround *forced* by the fact that `processid` is
  never captured anywhere upstream (confirmed: zero occurrences in `parser/process.py`) — but this
  substitution is not disclosed anywhere in the implementer's summary as a deviation from the
  task's literal instructions; it is presented as if "matched by page name" were simply the chosen
  design, not a compensating workaround for a missing upstream field. It is empirically safe for
  this one sample (no duplicate page names within any single artefact, confirmed by direct check)
  but is a latent fragility (BP does not strictly forbid duplicate subsheet names) that a
  `processid`-based match would not have.
- Implicit Block→Recover edge: as detailed above, **non-functional against real data** — the
  `exception_handler_id`-equality check can never be true because that field is never populated on
  any Recover stage anywhere in the real sample (verified directly). CLAUDE.md rule 4 and the
  task's own Do-step 2 describe this pairing as "the nearest enclosing Block in the same page,"
  which requires a document-order/nesting-based algorithm — not an ID lookup against a field that
  is never set. This part of Do-step 2 was not actually implemented, despite being claimed done.

### 5. `BPPage.reachable` default/mutation correctness

Confirmed sound: `BPPage` is genuinely frozen (`model_config = ConfigDict(frozen=True)`,
`models.py` line 358), and `_compute_reachability()` correctly reconstructs a **new** `BPPage`
instance with the computed `reachable` value wherever it differs from the default, verified
directly — 22 of 23 real pages in the AST output actually carry `reachable=False`, not a
silently-retained `True` default. The *mechanics* of applying the computed value to an immutable
model are correct; it is the computed *value* itself that is wrong (see §2/§4 above).

### 6. Orphan-page test validity

`Mark leftout Items as Exception` and `Send Info to Data Gateways` are indeed marked `reachable=False`
in the current AST output (re-verified independently, not just via the test). However, given that
21 of the other 21 non-orphan pages are *also* marked unreachable due to Bugs A/B, this test
currently provides no real signal that the algorithm distinguishes orphans from legitimately-called
pages — it would pass identically if the entire graph traversal were replaced with a no-op that
marks nothing but the entry page as reachable (which, in effect, is close to what's happening).

### 7. Test substitution / undisclosed weakening

Confirmed via diff: `test_pid171_reachable_pages_marked_correctly` — the task's own literal
Done-when test asking for `Get Mails`/`Populate Queue` to be marked reachable — was rewritten to
assert only `"the main page (is_main=True) is reachable"`, which is true by construction (the
algorithm unconditionally marks `main_page.page_id` visited the moment it finds a `Start` stage,
before any traversal even happens) and is therefore tautological, not a meaningful regression
test. This substitution is disclosed only under "Open questions" in the implementer's summary —
not listed under "Deviations," which the summary explicitly states is "None." Per the review
brief, this is a real deviation and should have been reported as such, ideally alongside a
recommendation to fix Bugs A/B before Task 4a could honestly be marked done, or an explicit
escalation to the coordinator for a scope decision (do Bugs A/B get fixed inside Task 4a, given
one of them — `ast/builder.py`'s `_SKIP_TYPES` — is literally inside this task's own file scope?).

## Most significant gaps

- **The task's own literal Done-when acceptance test (`Get Mails`/`Populate Queue` reachable) is
  currently false against the real sample**, and the test that would have proven this was quietly
  narrowed to a tautology (asserting only that the entry page is reachable) rather than being kept
  and reported as a blocking failure, or the situation escalated to the coordinator. This was
  disclosed only as an "open question," not flagged as a deviation despite the summary's explicit
  "Deviations: None" claim.
- **Two pre-existing bugs make the real-sample reachability computation almost entirely
  uninformative** (22 of 23 pages show unreachable): (a) `parser/process.py`'s main-page detection
  picks the wrong page as `is_main` (long-standing, predates this session); (b) `ast/builder.py`'s
  `_SKIP_TYPES` silently drops `Process`-type stages instead of normalising them to
  `ACTION(is_process_call=True)` per CLAUDE.md's own documented rule (also long-standing, but
  lives inside Task 4a's own declared file scope and directly blocks Do-step 1's required
  `processid` cross-reference mechanism). Fixing bug (b) is arguably in-scope for a Task 4a
  re-pass; bug (a) needs either an explicit scope exception or a new dedicated task, but should at
  minimum have been surfaced as a hard blocker rather than worked around silently.
- **The implicit Block→Recover edge reconstruction required by Do-step 2 is non-functional** — the
  `exception_handler_id`-based match never fires against real data (confirmed: that field is
  `None` on every stage in the real sample). The actual "nearest enclosing Block" pairing
  described in CLAUDE.md rule 4 was not implemented.
- **The SubSheet cross-reference match uses page name instead of the `processid` the task
  literally specifies** — a reasonable workaround given `processid` is never parsed upstream, but
  undisclosed as a deviation and a latent fragility (relies on stage name == target page name,
  unverified as a hard BP invariant).
- Two of the 13 full-suite failures (`test_pid_0171_page_with_password_item_emits_sensitive`,
  `test_sample_mandatory_flags_count`) were swept into the implementer's blanket "stale
  expectations, not errors" characterization without individual verification; at least the first
  looks like a real data-availability regression, not a number that merely needs updating.
- Minor: one uncaught `F541` ruff finding in the new test file.

## Verdict

**Needs another implementation pass.** The mechanical scaffolding (model field, frozen-model page
reconstruction, `build_ast()` shape handling, BFS traversal skeleton) is sound and the 35-error
full-suite reduction is real. But the task's central deliverable — a reachability model that
correctly identifies orphan pages on the real PID_0171 sample — currently produces a
near-degenerate result (1 reachable page out of 23) due to two identifiable, fixable defects, one
of which sits inside this task's own file scope (`ast/builder.py`'s `Process`-type stage handling).
The task's own literal acceptance test was quietly weakened to hide this rather than being kept
failing and escalated, which is the specific behavior CLAUDE.md's workflow discipline (report
gaps, don't silently work around them; never silently drop an untranslatable/unhandled construct)
exists to prevent. Recommend: (1) fix `_SKIP_TYPES`'s `Process`-type handling in `ast/builder.py`
per CLAUDE.md's own normalisation table (in-scope), (2) escalate the `process.py` main-page
mis-identification bug to the coordinator for a scope decision rather than working around it, (3)
implement the actual document-order/nesting-based Block→Recover pairing Do-step 2 calls for, (4)
restore the task's original named-page reachability test once (1)-(3) make it genuinely passable,
and (5) disclose the name-based SubSheet matching and the test substitution explicitly as
deviations in the next pass's summary.
