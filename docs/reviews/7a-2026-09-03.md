## Most significant gaps

1. **Rendered `WorkQueues` action parameters are literal, unsubstituted placeholder tokens
   (`<id>`, `<var>`, `<obj>`, `<msg>`, `<text>`), not real PAD syntax bound to the BP stage's
   actual data.** `mapping/vbo_catalogue.yaml`'s `method_actions` values are (and were already,
   for Excel/Outlook, pre-dating this task) documentation-shaped templates using the same
   `<placeholder>` convention as `vbo-action-mapping.md`'s table — they were never meant to be
   emitted byte-for-byte. Task 7a is the first task to actually wire a dispatch branch to consume
   `method_actions` directly, and it emits the template as-is with no substitution step, so every
   rendered `WorkQueues` call in the regenerated output (12 occurrences) contains non-functional
   angle-bracket text instead of real variable references (e.g. `obj_WorkQueueItem`,
   `txt_WorkQueueId`, or a mapped equivalent) that would need to come from `stage.params_map`
   (`Item ID`, `Queue Name`, `Exception Reason`, `Status`, etc. — all present and unused, confirmed
   by direct inspection of parsed `BPStage.params_map`).
2. **`Mark Exception`'s three documented status variants collapsed into one.** The required-reading
   table lists `BusinessException`/`ITException`/`GenericException` as three distinct outcomes
   depending on which exception-type branch calls `Mark Exception`; the single flat
   `method_actions["Mark Exception"]` template always renders `BusinessException`, so at least one
   of the `Mark Exception` `FUNCTION`'s two internal call sites now emits a status that doesn't
   match its actual branch context.
3. **The task's own "Done when" test doesn't catch either gap above** — it only asserts the action
   name substring is present and the TODO-stub substring is absent, so a run that emits invalid,
   unsubstituted PAD syntax still passes. The test should additionally assert real per-stage
   variable/parameter binding (or at minimum, absence of the literal `<...>` template-placeholder
   syntax) in the rendered output.
4. **Duplicate/parallel `method_actions` resolution logic.** `VBORouter.route()` already resolves
   `method_actions` into `resolved_action_template` (pre-dating this task, tested by
   `tests/mapper/test_vbo_router.py::TestMethodActionsPrecedence`), but `engine/annotator.py` never
   propagates it into `PAAnnotation`. Rather than noting this as a blocking gap outside its file
   scope, Task 7a added a second, independent lookup path directly inside `pad.py`
   (`_lookup_method_actions_template`) that duplicates the router's catalogue-lookup logic. This
   works for the narrow case tested here but leaves two mechanisms that could silently diverge as
   more `method_actions` entries are populated for other VBOs. `tests/mapper/test_vbo_router.py`
   was listed in this task's file scope but was not touched at all — no router-level test confirms
   the real `clsWorkQueuesActions` entries resolve correctly through the router's own path (they do,
   confirmed manually via `router.route(...)`, but nothing regression-tests it).

## Verdict

needs another implementation pass — the letter of the task's "Done when" condition (zero `# TODO`
stubs for the 4 documented methods, a passing test for `Get Next Item`) is met, and well-formedness
is clean, but the substantive goal of this task — real, working PAD syntax replacing placeholder
stubs — is not achieved: the "real syntax" now rendered is itself non-functional placeholder text
for every parameter, and one of the four wired methods (`Mark Exception`) silently mis-renders for
non-BusinessException branches. A follow-up pass needs to (a) substitute `<id>`/`<var>`/`<obj>`/
`<msg>`/`<text>` with real values derived from `stage.params_map` (or, at minimum, a real-looking
`%Var%`/quoted-literal PAD placeholder consistent with the rest of the generator, with a `# TODO`
noting the exact source expression, per CLAUDE.md's never-silently-drop rule) and (b) add the two
missing `Mark Exception` status variants (or select the correct one from stage/exception-type
context) before this can be called functionally complete.
