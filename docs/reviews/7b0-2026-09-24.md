## Most significant gaps

1. **All 36 binding `SET`s render a Python tuple repr.** In `src/flowsmith/generator/pad.py` L1228 to L1231, `translated_expr = self._translate_bp_expression(...)` is not unpacked, even though the signature at L1531 returns `tuple[str, list[str]]`. The `separate_actions` lines must also be emitted before the `SET`, as the Calculation path already does at L1913 to L1919. Counts: `grep -c "TO ('"` gives Loader 6 and Performer 30.
2. **No tests were written (Do item 6).** The commit touches only `pad.py` and `page_target_map.yaml`. The required synthetic-binding test would have caught gap 1.
3. **Output bindings and callee-side names are lost, and the implementer's explanation is wrong.** The BP XML carries the data. Call-stage `<output name=... stage="<caller data item>">` exists for `Get Mails` (`Mail Items`), `Get Input Data from Excel` (`FinalProduct_Collection`, `Sample ID`) and `Send mail` (`Items Completed`). Start/End `<input|output name=... stage="<callee data item>">` exists for every page, with mismatches such as `ScreenShot path` mapped to `File Path`, `Mail Items` to `Items`, `Parameter_WorkSheet_Name` to `Config_Parameter_WorkSheet_Name`, and `sheetName` to `SheetName`. `src/flowsmith/parser/process.py` L260 to L343 drops the `stage` attribute for both. Only inputs reach `params_map`. Outputs become name-only `BPDataItem`s. **Task 5b (L745 to L779) says nothing about populating call-stage output mappings**, so the claim that "Task 5b populates these" is unfounded. The implementer should have reported that `parser/process.py` (and possibly `BPStage`/`BPDataItem`) needs a scope extension to capture `stage=`. The generator also looks up outputs in `params_map`, which holds only *inputs* (L1255 to L1257). An output that shares an input's name would render the input *expression* as a SET target.
4. **The `split` branch does not bind (silent drop).** `Result Entry` (split) has 7 inputs and 1 output, and Performer L301 to L303 emits only the bare `CALL` with no binding and no TODO. This breaks both the section's split rule and the never-drop-silently rule.
5. **The Do item 5 clobber-risk report is missing.** The implementer said it "requires call-graph analysis outside the generator", but the Task 4a call graph already exists and the item was a report, not code. The regenerated output shows concrete hazards: (a) callee bodies re-initialise their own bound inputs at entry. For example, `Fetch Emails from Mailbox` sets `txt_Subject`/`txt_SenderMailID`/`txt_SenderName`/`txt_MailBoxName`/`txt_SubFolder TO %SomeVar%` at Loader L361 to L365 and L392 to L393, which overwrites the values bound at L108 to L113. `Send Email` does the same at Performer ~L751/L785. (b) `dtb_FinalProductCollection` is re-created with `DataTable.Create()` inside `Fetch Data from Excel file` (L655) and `Get Results by Analysis and SampleId` (L800), and `txt_SampleID` is set in 3 places (L422, L734, L819). Under all-GLOBAL scope these clobber the caller's data.
6. **The self-assignment skip is not implemented.** The "skip a `SET` where both sides resolve to the same PAD name" rule has no code, as Performer L305 shows. Once gap 3 is fixed, `ScreenShot path`→`[File Path]` should also collapse to a skipped `txt_FilePath`=`txt_FilePath`.
7. **An unmapped binding target has no TODO.** For `SET ScreenShot path` (Performer L286), `_render_page_call_bindings` falls back to the raw BP name when `variable_name_mapping` misses (L1215 to L1217, L1244 to L1246) instead of emitting the required `# TODO`.
8. **Do item 1 is incomplete (minor).** Hardcoded `is_global=False` remains at `pad.py` L276 (the legacy `generate_page` path, which still emits a non-GLOBAL `FUNCTION`), L777 and L931 (BLOCK renders, which are harmless because the template ignores it). The dead `is_global = True` local at L865 and the `is_global` conditional in `templates/pad/subflow.robin.j2` are leftover scope plumbing. They are harmless, but the done-condition asks for "no scope-decision logic left".
9. **Stale mapping note (minor).** `mapping/page_target_map.yaml` L126 still reads "parameterized by In_txt_DestinationFolder", which conflicts with the parameterless decision.

## Verdict

**Needs another implementation pass.** Gaps 1, 2, 4, 5, 6 and 7 are all inside the declared file
scope and can be fixed directly. Gap 3 needs a coordinator-approved scope extension to
`src/flowsmith/parser/process.py` (and the `BPStage`/`BPDataItem` models) so the parser captures the
`stage=` attribute on call-stage outputs and on Start/End inputs/outputs. This is a scope decision,
not a design decision. Without it, output bindings cannot be generated correctly, and inputs whose
parameter name differs from the bound data item will keep targeting a variable that the callee
body never reads.
