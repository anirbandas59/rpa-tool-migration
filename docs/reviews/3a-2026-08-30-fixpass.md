This supersedes `docs/reviews/3a-2026-08-30.md` (the first review, 30%, "needs another

`MultiArtefactRelease` contract). Since that review, an implementer fix pass migrated

main process apart from the sibling process and from VBOs") even though no existing test (old or
new) catches it.

8. **New finding — did NOT stop at re-confirming the top-level counts.** Per the review brief's
   instruction to "re-verify directly, don't just trust the prior review's confirmation carried
   over," inspected each artefact's *own* `pages` content, not just the artefact list length:
   ```
   p0 = r["processes"][0]  # PID_171_US_Process_LIMS_Prelude
   p1 = r["processes"][1]  # RPA_Sharepoint_API_ConfigFile_Download
   len(p0["pages"]) == len(p1["pages"]) == 381
   [pg["page_id"] for pg in p0["pages"]] == [pg["page_id"] for pg in p1["pages"]]  # True
   ```
   Every process **and every one of the 22 objects** ends up with the identical 381-page,
   full-document page/stage set. Root cause: `parse_element()`'s "full-document stage collection"
   step (`process.py` lines ~504–596, inherited unchanged from a pre-Task-3a commit that made
   sense when one XML document == one process) calls `root.iter(_ns("subsheet"))` /
   `root.iter(_ns("stage"))` against the **entire release document root**, which `parse_process()`
   now passes identically to every artefact's `parse_element()` call — so no artefact is actually
   scoped to its own `<process>`/`<object>` subtree. Reproduced the same defect with a minimal
   two-artefact synthetic XML fixture (one page in a `<process>`, a different page in a sibling
   `<object>`, same document) — both artefacts came back with **both** pages. This directly
   contradicts Task 3a's own Do step 2 ("distinguish the artefacts... so downstream code can tell
   the main process apart from the sibling process and from VBOs") — the artefacts are
   distinguished only by their top-level `name`/`process_id` metadata, not by their actual
   content. No test in the file (old or new, including the 4 tests added for Task 3a) catches
   this, because the new multi-artefact tests only assert on artefact *count* and top-level
   name/id fields, never on per-artefact page/stage identity or isolation.

## Most significant gaps

- **Per-artefact page/stage cross-contamination (new finding, most significant).**
  `parse_element()`'s full-document `root.iter(...)` stage/page collection (a leftover from when
  one XML document == one process, predating Task 3a) is now called identically for every
  process and object in a release, so every artefact ends up with the exact same full-document
  page/stage set instead of its own. Confirmed on both a synthetic 2-artefact fixture and the
  real `PID_0171.bprelease` (2 processes + 22 objects, all sharing the identical 381 pages). This
  is squarely inside `src/flowsmith/parser/process.py` (Task 3a's own file scope), not a Task 4a
  concern, and should be fixed — or at minimum explicitly flagged as a known limitation — before
  Task 4a/4b build call-graph or environment-variable wiring on top of it, since consuming
  `objects[i]["pages"]` today would silently hand Task 4a the entire process's logic under every
  VBO's name.
- **No test (old or new) exercises per-artefact page isolation.** The 4 new Task-3a tests
  (`test_multi_artefact_release_returns_correct_structure`,
  `test_multi_artefact_validation_count_mismatch`, `test_pid_0171_multi_artefact_parsing`,
  `test_backward_compat_single_process_file`) only assert on artefact *counts* and top-level
  `name`/`process_id` fields — never on whether one artefact's `pages` differ from another's. This
  should be added as a regression test alongside any fix.
- Minor, pre-existing, not from this fix pass: `F401` unused `Mapping` import in
  `src/flowsmith/parser/process.py` line 20.
- Minor: the fix pass's summary (and the coordinator's own framing) implicitly treats "core
  multi-artefact parsing logic itself does not need rework" as settled fact carried over from the
  first review — the first review's own verification (top-level counts only) wasn't deep enough
  to catch the defect above, which is a good example of why the review brief's "don't just trust
  the prior review's confirmation carried over" instruction mattered here.

## Verdict

**Needs another implementation pass** — narrowly scoped this time to fixing `parse_element`'s
per-artefact stage/page scoping (each artefact's page/stage collection must be confined to its
own `<process>`/`<object>` subtree, not the whole release document) plus a regression test that
would have caught it (e.g. assert two artefacts in the same release return disjoint `page_id`
sets, or that a VBO object's page count is far smaller than the main process's). The test-file
migration work that drove the previous 30% score is fully resolved and does not need to be
revisited.
