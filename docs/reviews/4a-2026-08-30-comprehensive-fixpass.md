### 2. Is "6 pages need deeper AST rearchitecting" real, or an in-scope wiring bug?

**An in-scope wiring bug, proven conclusively.** Traced predecessors of each of the 5 real
caller stages (`Mark Item As Exception`'s caller `ffb4d158-...`, `Mark as read...`'s caller
`aa2b6a2e-...`, `Send mail`'s two callers `d0547b46-...`/`a67912e4-...`) directly:

```
Mark Item As Exception call  ← predecessors: 'Tag Item' (ACTION), 'Resume1' (RESUME)
Mark as read... call         ← predecessors: 'System Exception?' (DECISION ontrue), 'Recover21'
Send mail call #1            ← predecessor: 'Capture Error Screenshot' (ACTION)
Send mail - No New Mail call ← predecessor: 'Resume3' (RESUME)
```

All four sit inside Main Page's exception-handling arm — real, functioning BP logic per §B15's
Block→Recover→circuit-breaker description. Dumped every `BLOCK`/`RECOVER` stage on Main Page and
its incoming edges directly: **all 5 Block stages and all 6 Recover stages have zero incoming
`onsuccess`/`ontrue`/`onfalse` edges anywhere in the process** — confirming these are pure
scope-boundary markers whose protected bodies are entered directly by mainline flow, exactly as
the anchor-fixpass review found for the one case it hand-traced.

The current `_compute_reachability` code only consults `block_recover_map` here:

```python
if current_stage.stage_type == StageType.BLOCK:
    recover_id = block_recover_map.get(current_stage.stage_id)
    if recover_id and recover_id not in visited_stages:
        to_visit_stages.append(recover_id)
```

Since no Block stage is ever popped from the BFS queue (zero incoming edges → never enqueued),
this branch **never executes** for any Block in the real sample. Proved this is not merely
theoretical but has literally zero effect: monkeypatched `_build_block_recover_map` to return
`{}` (fully ablating Fix 3) and re-ran `build_ast()` against the real sample — **identical output,
16 reachable / 8 unreachable, the exact same 8 pages**, both with and without the fix present.

This directly answers the review brief's core question: it is **not** a case where the caller is
"genuinely reached only through an exception-handling path the BFS doesn't traverse into" as a
matter of unavoidable architecture — it is a case where the map needed to make that traversal
possible was built (correctly — the `Work`→`Recover20` pairing it produces matches the exact real
semantic pairing identified by hand in the prior review), but never wired to fire under the
condition (zero-incoming-edge Blocks) the implementer's own docstring says is "the common case."
The fix that was actually needed — enqueue a page's Block→Recover targets whenever *any* stage on
that page becomes reachable (not gated on the Block stage itself being independently visited) —
is a same-file, mechanical BFS-wiring change, not a "deeper AST limitation" requiring
"rearchitecting how exception-handler scope membership is tracked," as the implementer's summary
frames it. This is the third time this project's review history has diagnosed this exact family
of defect (dead `exception_handler_id` check → document-order heuristic never exercised on real
data → "requires the Block to be independently reachable first" → now, after a claimed fix,
proven by ablation to still be exactly that same condition, unchanged).

### 3. MultipleCalculation fix (Fix 2) — verified correct

Read the real XML directly: `<stage ... type="MultipleCalculation">` bodies do store their
calculations under `<steps><calculation expression="..." stage="..." /></steps>` (confirmed
example: `Reset Consecutive Exception Indicators`, 2 nested `<calculation>` elements under
`<steps>`, no top-level `<calculation>` sibling). Independently re-built the real AST and counted:
**66 fanned-out `__calc_N` sub-stages, 0 with an empty `params_map`** — confirms the parser fix
(`process.py`'s new `<steps>` branch) genuinely populates every one, not just avoids a crash.
Redirect logic (`_apply_multiple_calculation_redirects`) is scoped correctly (only rewrites edges
whose target is a collapsed original MC ID) and does not fabricate edges.

One caveat, not a defect for this task's scope: every fanned-out `__calc_i` sub-stage inherits the
**same** `onsuccess_target` as the original MC stage (from `common_fields`, computed once before
the fan-out loop) rather than being chained `calc_1 → calc_2 → ... → calc_N → real target`. This
is sufficient for Task 4a's reachability/no-dangling-edges scope (every sub-stage's edge resolves
to a real stage) but means a future `FUNCTION`-rendering task will need its own logic to
sequence the N calculation lines correctly inside one `FUNCTION` body, not reuse this edge
structure as-is. Noting for the record, not scoring against this task.

### 4. Skip-type pass-through generalisation (Fix 1) — verified correct, including mixed chains

## Verdict

**Needs another implementation pass.** The task's own literal Done-when acceptance criterion
(`Get Mails`/`Populate Queue` reachable, the 2 named orphans unreachable) is met. But per the
explicit judgment call this review was asked to make: the remaining discrepancy is **not** an
appropriately-scoped, honestly-disclosed architectural limitation suitable for a tracked
follow-up. It is the same specific, mechanical, same-file BFS-wiring bug this review history has
now diagnosed three times in increasing detail, proven this cycle — by direct ablation — to still
have exactly zero effect on the real sample despite a claimed "structural, not BFS-dependent" fix.
Mischaracterising it as requiring "deeper AST limitations... rearchitecting how exception-handler
scope membership is tracked" would, if accepted, let a well-understood, already-recommended,
in-scope fix be permanently deferred under a false architecture-limitation banner. Recommend, in
priority order:

1. Fix `_compute_reachability` so a page's Block→Recover pairs are consulted whenever *any* stage
   on that page is reached by the BFS (or immediately once the page itself is marked visited), not
   only when the Block stage itself is independently popped off the BFS queue. This is the one
   remaining change needed to make the already-correctly-constructed `block_recover_map` actually
   do anything on real data.
2. Re-run reachability against the real sample after (1) and confirm it converges to 21-22
   reachable / 2-3 orphans (the 2 confirmed §B14 orphans, plus `Close Down` pending owner
   confirmation), not the current 16/8.
3. Reconcile `test_scorer.py`/`test_annotator.py`/`test_integration.py`'s hardcoded counts against
   the actual post-Fix-2 values (796 stages, 113 CALCULATION, not 725/42) — these numbers will
   shift again once (1) is fixed, so do this as the last step before declaring done, against a
   single final full-suite run.
4. Flag `Close Down`'s likely third-orphan status to whoever owns architecture doc §B14, citing the
   same `<processid>`-search methodology already used for the other two.
5. Consider persisting the Block→Recover pairing onto `BPStage`/`BPPage` (or a side-map returned
   alongside the AST) so Task 4b/rendering doesn't have to reconstruct it from scratch — raised in
   two prior reviews, still open.
