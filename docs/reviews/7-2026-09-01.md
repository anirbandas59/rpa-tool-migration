## Most significant gaps

1. **WorkQueues actions render as generic TODO stubs despite fully-documented, cited real PAD templates existing** (`docs/pad-reference/vbo-action-mapping.md`'s Work Queues table + `mapping/vbo_catalogue.yaml`'s own citation to it) — `Get Next Item`, `Mark Completed`, `Mark Exception`, `Update Status` all need a `method_actions` template wired into the catalogue; this is the single highest-leverage fix given WorkQueues is a shared VBO across the ~200-automation program.
2. **`GLOBAL.` qualification is entirely absent** (0 occurrences across both generated files) despite 15/16 Performer `FUNCTION`s being non-`GLOBAL` — this is the direct, named-in-the-architecture-doc cause of the broken consecutive-exception counter and any other cross-function state.
3. **Consecutive-exception pattern is non-functional**: counter resets to 0 on every call (no `GLOBAL.` persistence), the `Limit?` gating `IF` is an unfilled placeholder comment, and the dedicated `Send Consecutive Exception Mail`/`Send System Exception Mail` functions the architecture doc documents by line citation (§A7/§A8-D4) don't exist in the generated output or in `mapping/page_target_map.yaml`.
4. **Desktop Flow input contract diverges fundamentally from the reference**: 92 (Loader) / 111 (Performer) individually-named, unprefixed `@INPUT`s vs. the reference's exactly 1 (`In_txt_Config`) per flow — and the orchestrator itself only ever sends `In_txt_Config` (confirmed by decoding the packaged orchestrator's `RunUIFlow_V2` call), so the generated Desktop Flows' declared required-input surface doesn't match what will actually be supplied at call time.
5. **168 (Performer) + ~24 (Loader) unfilled Jinja-template placeholder lines and 139 literal `%SomeVar%` fallback assignments** — real business-rule expressions the Task 5b translator couldn't handle silently degrade to a commented-out template skeleton or a meaningless placeholder value, with only a confidence-banded name comment, not a `# TODO` naming the untranslated source expression (CLAUDE.md's "never silently drop a BP construct... leave a `# TODO` comment naming what it was and why" is not met here — the *stage* is named, but not *why* it failed or *what BP expression* needs manual completion).
6. **Orphan unreferenced Cloud Flow file** (`Workflows/Populate_Queue_cloudflow.json`) shipped in the `.zip` — leftover from the CLI still invoking the old per-page `CloudFlowGenerator.generate_process()` path (`cli/app.py:58`) alongside the new consolidated packaging path; violates Task 6b's own "exactly the file counts" done-condition and should be removed from the CLI/packager wiring.
7. **Orchestrator Cloud Flow content is stored inverted from the reference's documented convention** — real Logic-App JSON sits inline in `<Definition>` while the `<JsonFileName>`-referenced companion file is a hollow `{"package": ""}` stub; the reference (and architecture doc §A1) has it the other way around for Category-5 workflows.
8. **`Load Config Data` FUNCTION** (present in the reference Loader) has no entry in `mapping/page_target_map.yaml` and is missing entirely from generated output, with no documented rationale (unlike the four legitimately-`stop`-shaped orphan pages, which are cited with reasons).
