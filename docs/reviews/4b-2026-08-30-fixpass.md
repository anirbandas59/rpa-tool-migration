## Verification performed

### 1. Fix 1 (Block→Recover-aware role-tagging BFS) — genuinely fixed, ablation reproduced independently

Read `_tag_loader_performer_roles()` directly (`src/flowsmith/ast/builder.py:991-1257`). It now
accepts `block_recover_map` as a parameter and both Phase 1 (loader-side, lines 1086-1098) and
Phase 2 (performer-side, lines 1181-1193) BFS loops consult it with the identical logic already
present in `_compute_reachability`'s Fix A (lines 887-899) — checking, on every newly-reached page,
whether any Block on that page has a paired Recover not yet visited, and enqueuing the Recover if
so. This is present in *both* phases, not cosmetically referenced in only one.

Ran an independent ablation against the real `PID_0171.bprelease` sample (via `parse_process()` +
`build_ast()`, matching the `pid_0171_process` fixture's own path):

```
=== Normal (post-fix) run ===
Mark Item As Exception                             reachable=True role=performer
Send mail                                          reachable=True role=performer
Mark as read and move to exception folder          reachable=True role=performer
Send mail - No New Mail                            reachable=True role=performer
Completed No Outcome                               reachable=True role=performer

Get Mails / Populate Queue / Save Attachments / Result Entry:
Populate Queue                                     reachable=True role=loader
Get Mails                                          reachable=True role=loader
Save Attachments                                   reachable=True role=performer
Result Entry                                       reachable=True role=performer

=== Ablated run (empty block_recover_map passed into _tag_loader_performer_roles) ===
Mark Item As Exception                             reachable=True role=None

Send mail - No New Mail                            reachable=True role=None
Completed No Outcome                               reachable=True role=None
```

This exactly reproduces the implementer's claimed before/after and the original bug signature from
the first review — confirming the fix has real causal effect, not merely a plausible-looking
change. All 6 named pages from the task's step 4 and this pass's summary are correctly tagged.

**Residual architectural note (not a functional defect):** no shared helper was extracted for the
"consult block_recover_map on newly-reached page" logic — `_compute_reachability`, Phase 1, and
Phase 2 each have their own copy (confirmed by `grep`; no new `def` between `_build_block_recover_map`
and `build_ast`). The prior review's concern about *two* independently-maintained BFS
implementations for the same graph concept is not resolved architecturally — it is now *three*
copies that happen to agree today. This is a legitimate, if secondary, drift risk for whoever next
touches reachability logic, not a present-day correctness problem.

### 3. Fix 4 (password-item test) — genuinely end-to-end, but confounded on the specific mechanism it claims to test

Read `test_pid_0171_page_with_password_item_emits_sensitive` (`tests/generator/test_pad.py:875-948`)
directly. It now: parses the real release, finds a secondary process (not the main one — correctly
matching the documented fact that PID_0171's main process has zero password items) with a
password-typed data item, calls `build_ast()` on it, runs `create_annotator().annotate_process()`,
calls `PADGenerator().generate_page()`, and asserts `"@SENSITIVE: ["` appears in the generated text.
This is a real pipeline exercise, not the previous pass's tautological `assert password_item is not None`.

However, mutation-testing the generator's actual sensitivity logic (`src/flowsmith/generator/pad.py`'s
`SENSITIVE_DATA_TYPES`/`_collect_sensitive_vars`) shows the test would **not** catch a regression in
the specific "password `data_type` → sensitive" mechanism it is nominally validating:

- Removing `"password"` from `SENSITIVE_DATA_TYPES` (leaving `SENSITIVE_NAME_TOKENS` untouched) —
  i.e. completely disabling the data-type-based sensitivity path this test is meant to protect —
  the test **still passes**, because the same secondary process's page also has other
  password-typed items whose *names* independently contain `"secret"`/`"key"` (e.g. `Client Secret`,
  `SAS Key`), which trigger `@SENSITIVE: [` via the unrelated name-heuristic path regardless.
- The real password-typed item the test finds (`Client ID`) genuinely *is* included in the
  `@SENSITIVE` list today, and its name contains none of the sensitive name tokens — so it
  legitimately demonstrates the data-type path works in the current, correct code. But the test's
  only assertion (`"@SENSITIVE: [" in result`) checks for the bracket's mere presence, not that
  `password_item_name` (`Client ID`) specifically appears in it — so it can't distinguish "the
  data-type mechanism works" from "some other item on the same page happens to be sensitive for an
  unrelated reason."
- Restored the file to its original state after the mutation test (`git diff` confirms no residual
  changes to `generator/pad.py`).

This is a real, demonstrated weakness, but a materially smaller one than the prior review's finding
(a trivially-true assertion reachable only after a skip branch) — this test is a legitimate,
non-trivial pipeline exercise that just isn't precise enough to isolate the one thing it's named
for. A one-line strengthening (`assert password_item.name in result` in addition to the existing
check) would close this. Not blocking, but worth a follow-up note.

  Phase 1 and Phase 2 of `_tag_loader_performer_roles`) rather than unified into one shared helper.
  Functionally correct today (ablation-confirmed), but a latent drift risk if one copy is edited
  without the others — the prior review's architectural concern was patched at the symptom level,
  not resolved structurally. Recommend a follow-up (out of this task's declared scope) to extract a
  shared `_extend_via_block_recover(page, visited_stages, to_visit, block_recover_map, stage_to_page)`-
  style helper.

  pipeline end-to-end but would not fail if the specific "password `data_type` → sensitive" logic
  broke, because another item on the same test page independently triggers `@SENSITIVE` via the
  unrelated name-heuristic path. A one-line strengthening (assert the specific password-typed
  item's name appears in the emitted list) would close this without needing a new fixture.
