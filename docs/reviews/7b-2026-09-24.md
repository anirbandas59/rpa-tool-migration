## Coordinator concerns, checked one by one

1. **The 8 `test_flag_index` failures predate 7b and are not caused by it.** I made a sparse worktree at `79719aa` (src/tests/mapping/templates), copied in the untracked `samples/blueprism/PID_0127.bprelease`, and confirmed imports resolved to the worktree's `pad.py` (no `MAIN_BODY_VARIABLES`). Running `tests/engine/test_flag_index.py tests/mapper/test_vbo_router.py` gave the **same 10 failures** (8 flag_index + 2 router). The dependency graph agrees: `test_flag_index.py` imports only `flowsmith.ast`/`engine`/`exceptions`, and 7b touched none of them. The worktree has been removed.
2. **`MAIN_BODY_VARIABLES` is a PID_171-specific hardcoded list, not an AST derivation.** It breaks CLAUDE.md's "YAML mapping config lives in mapping/ — never hardcode mappings in Python" and the rollout rule that conversion must work deterministically for ~199 other automations. A data-driven version is feasible. BP marks page visibility with `<private/>`: 39 Main-page Data/Collection items, 25 of them private. The AST already carries `page.data_items`, so a Main-page-data-item / cross-page-reference derivation could be built from `pad.py`. `BPDataItem` has no visibility field (`ast/models.py` L176-196), so full `<private/>` fidelity would need a parser/AST extension. That is out of 7b's file scope and should have been reported, not replaced by a hardcoded list.
3. **Mark Exception is hand-written Python keyed off the page name, and it silently discards the real BP stages.** Details are in the FUNCTION fidelity row. The PAD syntax is textually faithful to reference L1239-1320, but citations are block-level comments ("L1239-L1257 of reference"), not line-by-line. The code copies the reference's D6 deviation instead of BP ground truth and does not flag the choice. The variant "dispatch" is a PAD-level `IF` on `GLOBAL.txt_ExceptionType` inside a fixed string, not generator-side selection from catalogue variants. Counter and limit names: the rendered `num_ConsecutiveExcCount`/`ExcLimit` are right (reference L25/L145/L1277/L1283, §A4, §A7). The task text's `num_ConsecutiveExceptionCount` is the stale name that review 7 quoted from the pre-7b generated output (BP data item "Consecutive Exception Count" mapped mechanically). The done-when wording should be corrected, not the code.
4. **Both send-mail FUNCTIONs are empty TODO stubs, not invented content.** Neither has a BP page (the BP release has no "Send Consecutive Exception Mail"/"Send System Exception Mail" subsheet), so the new `page_target_map.yaml` entries (L148-162) are keyed on BP page names that do not exist and are dead config. Their `citation` fields point at reference **call sites** (L1283-1302/L1300, L1303-1319/L1318), not the FUNCTION definitions the task names (L1026, L1096), and not a §B14 row, which the file header requires ("Every entry MUST cite its source row from §B14"). The stubs are emitted by substring-matching `"CALL 'Send ...'" in full_content` (`pad.py` L510-527), so they exist only because the hardcoded Mark Exception string contains those CALLs. They declare no parameters, but callers pass 5.
5. **The tests do not test what the done-condition asks for.** `test_mark_exception_variant_selection_is_deferred_to_task_7b` now asserts the opposite of its name. `test_mark_exception_counter_persists_across_calls` greps for `GLOBAL.num_ConsecutiveExcCount` substrings. Nothing simulates consecutive calls or checks that nothing resets or shadows the counter between items (for example, no check for main-body initialisation or the Mark Complete reset). `test_global_qualification_in_functions` passes only because the hardcoded Mark Exception string contains every asserted token, so it would still pass with `_needs_global_qualification` deleted. All three are string-presence checks on a string the implementation writes verbatim.
6. **GLOBAL. side effects.** Real regenerated output differs from pre-7b output **only** in the Mark Exception body and the 2 appended stubs (diff hunks `482,515c482,562` and `1330a1378,1389`; Loader has 0 diff lines). So there are no regressions elsewhere, but also no §A4 effect elsewhere. Latent defects in the new helper: double `GLOBAL.GLOBAL.` prefixing; LHS writes left unqualified while RHS reads are qualified, which recreates the exact shadow bug §A4 describes; main-body context defaults to "non-GLOBAL function"; and the function-local `flg_QueueUpdateSuccess` is listed as main-body state.

## Most significant gaps
- **Do 1 not delivered in real output.** 0 rule-derived `GLOBAL.` qualifications; 65 unqualified main-body references in 10 non-GLOBAL Performer FUNCTIONs (e.g. `Fetch Data from Excel file` L684/687). The only `GLOBAL.` text comes from a hardcoded string.
- **`MAIN_BODY_VARIABLES` is a hardcoded PID_171 list in Python** (`pad.py` L82-127). This breaks the mapping-in-YAML rule and the 200-automation determinism requirement. It also misclassifies `flg_QueueUpdateSuccess`.
- **The Mark Exception FUNCTION is a copied reference transcript that ignores `page.stages`** (`pad.py` L927, L954-1104). It silently drops the BP Tag Item, Defer, Not Completed, Completed No Outcome and TERMINATE stages with no `# TODO`, and it copies the D6 regression without flagging it.
- **Do 4 not delivered.** The catalogue variants `Mark Exception :: ITException/GenericException` are never consumed; the status templates are duplicated as Python literals. The `# VERIFY ... deferred to Task 7b` emitter remains live at `pad.py` L2265-2266.
- **The consecutive-exception state is never set up anywhere else, so the pattern does nothing end to end.** Counter and limit are never initialised or loaded, `flg_HaltRun` is never checked, and the Mark Complete reset is still a placeholder (generated L475-476).
- **Dangling call signatures.** CALLs pass 5 `In_*` args to 3 parameterless FUNCTIONs. `obj_WorkQueueItem` is never passed into or set in Mark Exception.
- **The send-mail stubs are poorly wired.** They cite call sites instead of L1026/L1096. The `page_target_map.yaml` entries (L148-162) are keyed on nonexistent BP pages and have no §B14 citation. The stubs are triggered by substring matching on generated text.
- **Qualification helper bugs:** `GLOBAL.GLOBAL.` double prefix; LHS writes not qualified; main-body context treated as a non-GLOBAL function.
- **The tests are tautological string-greps.** None simulates consecutive calls, and one test name contradicts its assertions.

## Verdict
**Needs another implementation pass.** Most of the work is plain implementation: derive main-body variables instead of hardcoding them, qualify LHS writes, fix the double prefix, translate the Mark Exception page from its stages using the catalogue variant keys, and carry the In_/Out_ parameters. Two design decisions should go to the coordinator before that pass, so they are not guessed again:
1. **Mark Exception target semantics.** Should the generator reproduce BP ground truth (§A7: reset-to-0 and terminal on mismatch; breach via TERMINATE/SUE) or the `_11_managed` D6 behaviour (unconditional increment)? §A8 D6 calls the latter a regression.
2. **PAD-only FUNCTIONs with no BP page** (`Send Consecutive/System Exception Mail`). Should they be emitted from a cited catalogue/template entry in `mapping/`, reproducing ref L1026-1060/L1096-1131, or stay TODO stubs? If they stay stubs, they must at least declare the 5 `In_*` parameters their callers pass. A related scope question: carrying BP `<private/>` visibility into `BPDataItem` would need a parser/AST change outside 7b's file scope.
