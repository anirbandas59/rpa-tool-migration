## What changed since the prior review

- `cloudflow.py._resolve_init_email_recipient()` now returns two distinct values:
  `init_email_recipient` (for the `To` field — resolves `Generic_SupportTeam_EmailID` to
  `@parameters('<schema_name>')`, or a `# TODO` placeholder string if the env var is absent) and
  `init_failure_email_expr` (a hardcoded coalesce of `Try:_Init`'s own action outputs,
  `Compose:_Config`/`Set_Config_value`, with a `'Configuration initialization failed'` literal
  fallback).
- `templates/cloudflow/orchestrator.json.j2` now renders `{{ init_email_recipient }}` at the
  `emailMessage/To` site (line 333) and `{{ init_failure_email_expr }}` at the `Exception_Message`
  `SetVariable` site (line 320) — previously both sites rendered the same variable.
- Two Jinja2 `{# ... #}` comments were added immediately before the two intentionally-empty
  placeholder branches (`If_Loader_type_=_Cloud`'s true branch, line 113; `If_Performer_type_=_desktop`'s
  else-branch nested `If`, line 273), each citing architecture doc §A2 line numbers and the
  "STOP if a real BP process ever needs this path" language from Do-step 3.
- `Catch:_Global_Error_Handler`'s email subject/body were reverted back to the exact pre-Task-6a2
  baseline (`git show 34d5a9c:templates/cloudflow/orchestrator.json.j2` — `"- System Exception"`
  subject, `Action: @{first(body('Filter_array'))?['name']}` restored in the body) — confirmed by
  diffing against that commit directly, not just trusting the claim.
