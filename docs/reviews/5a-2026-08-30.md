**The claimed file/function counts, orphan-exclusion, and test-suite numbers all check out exactly

implementer to verify were not caught, and materially undermine the "matches the real
Loader/Performer shape" done-condition:

1. **`CALL '<page name>'` targets don't match the `FUNCTION '<page name>' GLOBAL` declarations
   they're supposed to call**, for any page whose name contains a space — a dangling reference in
   nearly every cross-page call in the generated output.
2. **The Loader's main body is the wrong content.** Per architecture doc §B11/§A3 (both cited in
   this task's own "Required reading"), Main Page is a *split* page — its own pre-`Get Next Item`
   stages are supposed to become the Loader's main body. The AST has no mechanism to split a page,
   Task 4b's role-tagger resolves this by giving Main Page a single atomic role
   (`performer`, "priority: performer > loader"), and Task 5a's `entry_page` selection
   (`next(p.is_main) or pages[0]`) never notices — it silently falls back to whichever loader-role
   page happens to be first in list order (`Populate Queue`), so the actual BP entry-point content
   (config parsing, `Get User Name`, `Delete Config File`, the two calls that populate the queue)
   never appears in the Loader `.robin` file at all.

Neither is mentioned in the implementer's summary ("Deviations: None claimed. Open questions: None
claimed."), despite both being discoverable from the task's own required reading and its own
explicit verification instructions (step 2's "check it still fires correctly," and the entry-point
selection this review was asked to scrutinise).

## Verification detail

**1. Structural shape vs. reference files.** `uv run flowsmith convert` on the real sample
produces exactly 2 `.robin` files (`PID_171_US_Process_LIMS_Prelude_Loader.robin` 320 lines/3
`FUNCTION` blocks, `..._Performer.robin` 1302 lines/16 `FUNCTION` blocks — matches the
implementer's reported 321/3 and 1303/16 within a trailing-newline rounding difference). The
skeleton (header → main body, no wrapper → `FUNCTION '<name>' GLOBAL ... END FUNCTION` blocks) is
the right shape. Header directive counts are correct — `@@ConnectionString`, `IMPORT` (x2),
`@SENSITIVE` each appear exactly once per file, confirming step 5 ("fire once per output file")
was done correctly.

However, header **content** diverges sharply from the reference: the real Loader has exactly one
`@INPUT` (`In_txt_Config`) and two `@OUTPUT`s; the generated Loader has **46** `@INPUT` lines
(`QueueName`, `Lock Name`, `Mail Items`, `Timeout`, `Preferred Token`, …) and **zero** `@OUTPUT`
lines; the generated Performer has **111** `@INPUT` lines and zero `@OUTPUT`s. These are
stage-level VBO call parameter names (`data_item.is_input` on individual `ACTION` stages), not
process-level flow inputs — the architecture doc is explicit (§A3 line 671) that a flow's
`@INPUT`/`@OUTPUT` should be driven by Main Page's `Start`/`End` data items, not a union of every
stage's own parameter names. This input-collection logic itself predates Task 5a (verified via
`git diff HEAD` — the loop body is byte-identical to the one already in the untouched
`generate_page()`), and `@OUTPUT` support has never existed anywhere in `pad.py` or
`flow_header.robin.j2`. But Task 5a's consolidation is what turned this from a small, easy-to-miss
per-page nuisance into a 46–111-line union spanning every page folded into a role — and the
implementer's summary claims "Verification against real PID_0171.bprelease" without surfacing
either the input explosion or the total absence of `@OUTPUT`, both directly visible in the file
they say they inspected.

**2. `CALL`/`FUNCTION` name consistency (step 2's explicit check).** Confirmed broken. Example from
the generated Performer file: `CALL 'Mark Item As Exception'` (line 135, raw, unsanitised page
name) vs. `FUNCTION 'Mark_Item_As_Exception' GLOBAL` (line 330, sanitised via
`_sanitise_filename`/`flow_file_stem`, which turns spaces into underscores). These do not match —
in real PAD this is a dangling call, exactly the class of defect `docs/bp-to-pad-...` calls a
well-formedness violation. The cause: `_render_stage`'s `RunDesktopFlow`/`SubFlow` branch
(`pad.py:456-461`, untouched by this task's diff) renders `call_template.render(subflow_name=
stage.name)` — the **raw** stage/page name — while `_render_page_as_function` (new in this task)
renders the `FUNCTION` header via `self._sanitise_filename(page.name)` — the **sanitised** name.
Every multi-word page name that gets called cross-page is affected: `Launch_Sample Manager` /
`Launch_Sample_Manager`, `Read Excel As Collection` / `Read_Excel_As_Collection`,
`Mark as read mail and move Exception Folder` / (doesn't even match the FUNCTION `Mark_as_read_
and_move_to_exception_folder` — different words entirely, a second, independent defect in the
`CALL` target derivation for at least one stage). Single-word names (`DataGateway`) happen to
survive. This directly contradicts the "Deviations: None" / "Test result... consolidation... fires
correctly" implication in the implementer's summary — step 2 told them to check this exact thing.

**3. Entry-point selection.** Confirmed via `ast/builder.py::_tag_loader_performer_roles` (lines
1239-1261): Main Page is reachable both before and after `Get Next Item`, and the role-assignment
priority is `"performer" > "loader"` — so Main Page's role is unconditionally `performer`, and
`is_main=True` sits only on that one page. In `generate_process`, `entry_page = next((p for p in
pages if p.is_main), pages[0])` for the Loader group therefore never finds an `is_main` page and
falls back to `pages[0]` — whichever loader-tagged page appears first in `process.pages` list
order (`Populate Queue`, confirmed against the generated file: its content — "Aquire Lock,"
"Release Lock," `clsEnvironmentLockingBusinessObject` STUB comments — matches architecture doc
§B14 row 2's description of the `Populate Queue` page, not Main Page's actual init sequence
described in §A3 lines 160-162: default-setting, `In_txt_Config` parsing, `CALL 'Load Config
Data'`). The real Loader's `Get unprocessed emails`/`Add to Queue Block` structure (§A3) is Main
Page's own pre-split body with `Get Mails`/`Populate Queue` content *fused into* it as `BLOCK`s —
not `Populate Queue`'s raw stage list standing in as the entry body. This is a foreseeable gap
directly readable from the task's own required §B11 reading; it isn't flagged anywhere in the
implementer's summary. It may be a genuine, deeper design gap inherited from Task 4b (whose "Do"
list only covers whole-page role tagging, not splitting a single page mid-stage-list) rather than
something 5a could fix within its own file scope — but the task's own review checklist explicitly
asked "is this the actual page BP executes first," and the honest answer is no, and that should
have been surfaced as an open question rather than left silent.

## Most significant gaps

- **`CALL '<page name>'` targets don't match their sanitised `FUNCTION '<page name>' GLOBAL`
  declarations** for any page name containing a space — breaks nearly every cross-page call in the
  consolidated output. This is exactly what the task's own step 2 asked the implementer to verify,
  and it wasn't caught. Root cause: `_render_stage`'s `RunDesktopFlow`/`SubFlow` branch renders
  `stage.name` raw while `_render_page_as_function` renders `_sanitise_filename(page.name)`.
- **The Loader's main body is the wrong page's content.** Main Page (the real BP entry point,
  split at `Get Next Item` per §B11) is atomically tagged `role: "performer"` by Task 4b's
  "performer > loader" priority rule and carries the only `is_main=True` flag, so Task 5a's
  `entry_page` selection for the Loader role silently falls back to `pages[0]` (`Populate Queue`)
  instead of any portion of Main Page — the Loader `.robin` file never contains Main Page's actual
  init/config-parse logic at all. This is discoverable from the task's own required §B11/§A3
  reading and wasn't flagged as an open question.
- **Flow-header `@INPUT`/`@OUTPUT` content is badly wrong** relative to the reference shape this
  task was asked to match: 46–111 spurious `@INPUT` lines sourced from stage-level VBO call
  parameters (pre-existing collection logic, but newly amplified by cross-page consolidation) and
  zero `@OUTPUT` lines in either file (a capability that has never existed in `pad.py`). Neither is
  mentioned in the implementer's "verification against the real sample."
- Minor: `generate_page()` is now dead in the CLI path but still carries ~30 tests and a template
  dependency; not flagged as deprecated/leftover in the summary. `tests/e2e/test_pid171_pipeline.
  py`'s `test_definitions_wrap_body_in_a_function` docstring is now inaccurate (post-consolidation,
  a Definition legitimately has multiple `FUNCTION` blocks) but out of this task's declared scope
  to fix.
