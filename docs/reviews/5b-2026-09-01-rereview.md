## Finding 1: Done-when test — DOES NOT EXIST AS SPECIFIED

The Done-when criterion is:

> "a new test asserts that generating a `Calculation` stage with a known BP expression
> (e.g. `[Exception Type]` assignment) produces the exact expected `SET txt_ExceptionType TO ...`
> line, **not a placeholder**."

**What exists instead:** The closest test is
`test_calculation_stage_uses_variable_name_mapping_for_target` (line 864). It does NOT satisfy
the Done-when:

- It tests a **dotted collection target** (`FinalProduct_Collection.Column8` → `[Output_value]`),
  not an `[Exception Type]` assignment.
- Its assertion is a **weak disjunction**: `assert ("dtb_FinalProductCollection.Column8" in result
  OR "FinalProduct_Collection.Column8" not in result)`. The second branch of this `or` is trivially
  true if the BP raw name was never present in the result to begin with. This assertion **cannot
  fail** if the mapping is absent — it would still pass. This is a fundamentally invalid test
  assertion.
- It does **not assert a non-placeholder value** on the right side of the SET (the expression
  `[Output_value]` would be translated to `Output_value` if no mapping exists, which is not
  `%SomeVar%` either — but neither is it the correct real value).

There is a `test_translate_bp_expression_converts_brackets_to_variables` test (line 793) that
does call `_translate_bp_expression` with `"[Exception Type]"` and asserts `result ==
"txt_ExceptionType"`. However, this tests the **internal helper in isolation** — it does not test
that a `Calculation` **stage** generates a specific `SET ... TO ...` **line** in the generated
output. The Done-when explicitly requires end-to-end stage rendering ("generating a Calculation
stage ... produces the exact expected `SET txt_ExceptionType TO ...` line, not a placeholder").

**Verdict on Done-when: FAIL.** No test drives a `Calculation` stage through `_render_stage`
with an `[Exception Type]` → `txt_ExceptionType` assignment and asserts the exact output line.

## Finding 2: Do-step 1 — `%SomeVar%` on value side — partially addressed, substantially still present

Fresh corpus numbers (commit 20991cb):

| File | Total SET | SomeVar value-side | Real-expression value-side |
|---|---|---|---|
| Performer.robin | 193 | 115 (60%) | 78 (40%) |
| Loader.robin | 40 | 24 (60%) | 16 (40%) |

**60% of all SET statements still have `%SomeVar%` as the value expression.** The prior review
accepted this as "VBO action output expressions are not yet translated (Do-step 3's permanently
deferred scope)." That framing is partially correct — many of these are VBO output params.
However:

- Lines like `SET txt_ExceptionType TO %SomeVar% # VERIFY: Exception Type` and
  `SET txt_ExceptionDetail TO %SomeVar% # VERIFY: Exception Detail` are **CALCULATION-stage
  outputs**, not VBO action outputs. These should have been wired with real BP expression
  translation per Do-step 1 — `[Exception Type]` → `txt_ExceptionType`. Instead they emit
  `%SomeVar%`.
- The prior review said "The `%SomeVar%` is a placeholder for the *value* side ... the VBO action
  output expressions are not yet translated." But the lines above are not VBO action outputs;
  they are `CALCULATION` stages whose value expressions were not translated.

**This is a Do-step 1 failure that was incorrectly attributed to Do-step 3 deferral** in the
prior review. Some of the `%SomeVar%` on value-sides genuinely are VBO outputs (deferred), but
others are Calculation stages whose expressions should have been translated and were not.

The `_translate_bp_expression` method exists and correctly translates `[Data Item]` → variable
reference, but it is only invoked when `_render_stage` is called with the `variable_name_mapping`
argument populated. For these specific Calculation stages that still emit `%SomeVar%`, the
evidence is that either: (a) the mapping lookup fails to find the key and falls back to the
placeholder, or (b) the rendering path does not call `_translate_bp_expression` for those
stages' value expressions.

## Finding 5: Test assertion quality — `test_calculation_stage_uses_variable_name_mapping_for_target`

The assertion at line 896–899:
```python
assert (
    "dtb_FinalProductCollection.Column8" in result
    or "FinalProduct_Collection.Column8" not in result
)
```

This is a logically defective assertion. The second disjunct (`"FinalProduct_Collection.Column8"
not in result`) is trivially true any time the raw BP name was transformed to anything at all —
even to `%SomeVar%` or an empty string. The test **cannot detect a regression where the mapping
is not applied**. It would pass even if `_render_stage` completely ignored the mapping. This test
provides zero regression protection for its stated goal.

## Most significant gaps (ordered by severity)

### 1. Done-when criterion is unmet — BLOCKING

The explicit Done-when test does not exist. No test:
- Takes a `Calculation` stage with a known BP expression (`[Exception Type]` assignment)
- Drives it through `_render_stage` end-to-end
- Asserts the exact output line `SET txt_ExceptionType TO txt_ExceptionType` (or similar
  real value — not `%SomeVar%`, not a stub)

The `test_translate_bp_expression_converts_brackets_to_variables` test covers the internal
helper in isolation only. The `test_calculation_stage_uses_variable_name_mapping_for_target`
test has a logically defective assertion.

### 2. `%SomeVar%` on CALCULATION-stage value sides — real Do-step 1 gap

60% of all SET statements use `%SomeVar%` as the value. The prior review blanket-attributed this
to VBO output expressions (Do-step 3, deferred). On re-inspection, lines like:
```
SET txt_ExceptionType TO %SomeVar% # VERIFY: Exception Type
SET txt_ExceptionDetail TO %SomeVar% # VERIFY: Exception Detail
```
are output parameters from VBO action calls (WorkQueues Get Next Item outputs), not
raw CALCULATION stages. But the presence of these lines indicates that even where the target is
correctly prefixed/named, the value side is not translated. The `_translate_bp_expression`
method exists and works for `[Data Item]` → variable references, but the rendering path for
VBO output parameter expressions hits the `%SomeVar%` fallback. The Do-step 1 requirement
("wire the real stage data") is only half-met: **target side** is correctly named, **value side**
is not translated for most stages.

### 3. `test_calculation_stage_uses_variable_name_mapping_for_target` assertion is logically void

```python
assert (
    "dtb_FinalProductCollection.Column8" in result
    or "FinalProduct_Collection.Column8" not in result   # ← trivially true if name was transformed at all
)
```
This assertion cannot detect a regression. It passes if the mapping is not applied, if the name
is replaced by `%SomeVar%`, or if the rendering ignores the input entirely. This test needs to be
rewritten to assert the positive case only: `assert "dtb_FinalProductCollection.Column8" in result`.

`_apply_type_prefix` docstring at pad.py:1137 still shows old camelCase examples
(`num_retryCount`, `dtb_finalproductCollection`). `_resolve_dotted_reference` docstring at

### 5. `import re` inside function body (pre-existing, non-blocking)

## Verdict

**Needs another implementation pass.**

The explicit Done-when criterion ("a new test asserts that generating a Calculation stage with a
known BP expression produces the exact expected `SET txt_ExceptionType TO ...` line, not a
placeholder") is not met. The closest existing test (`test_calculation_stage_uses_variable_name_mapping_for_target`)
uses a logically defective assertion that cannot fail. The expression-translation unit test
(`test_translate_bp_expression_converts_brackets_to_variables`) covers the internal helper only,
not end-to-end stage rendering.

**Minimum required for a passing re-review:**
1. Add a test that calls `gen._render_stage(calc_stage, process, {}, mapping)` with a
   `Calculation` stage whose `params_map = {"Exception Type": "[Exception Type]"}` and mapping
   `{"exception type": "txt_ExceptionType"}`, and asserts `"SET txt_ExceptionType TO txt_ExceptionType"` (or the
   correct translated form) appears in the output — not `%SomeVar%`.
2. Fix `test_calculation_stage_uses_variable_name_mapping_for_target`'s assertion to be a strict
   positive check rather than a disjunction.

**Accepted-deferred (not blocking this pass):**
- `%SomeVar%` on VBO output value-side expressions (Do-step 3, deferred)
- Trim/Lower 0 invocations (no corpus data)
- `num_ConsecutiveExceptionCount` vs. `num_ConsecutiveExcCount` spelling gap
- `GLOBAL.` qualification (Task 5c scope)
- Stale docstrings
- `import re` inside function body
