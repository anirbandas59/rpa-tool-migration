### 3. NEW, significant finding: `method_actions` keys don't match real action strings for the majority of this task's own additions

The mapping-yaml-conventions rule (`.claude/rules/mapping-yaml-conventions.md`) and the catalogue
file's own header both state the contract: `method_patterns — method name substrings seen in this
sample`. Neither prior review checked the literal `action="..."` attribute Blue Prism actually
records for real stages calling these VBOs. Doing so now (`grep -o 'resource
object="<VBO>" action="[^"]*"' samples/blueprism/PID_0171.bprelease`) and cross-referencing against
a live `router.route()` call for every real stage in the sample (`build_ast` → `VBORouter.route`
per real stage, checking `resolved_action_template`) gives:

| VBO | `method_actions` key added by Task 2b | Real `action=` string(s) actually used in `PID_0171.bprelease` | Fires? |
|---|---|---|---|
| `MS Excel VBO` | `Get Worksheet As Collection` | `Get Worksheet As Collection` (×4) | **YES** |
| `MS Excel VBO` | `Write to cell` | `Write Collection` (×1) | **NO — never matches** |
| `MS Excel VBO` | `Save As` | `Save Current Workbook As` (×1) | **NO — never matches** |
| `MS Outlook Email VBO Extended` | `Get Received Items`, `Mark Email As Read`, `Move Email` | only `Save Attachments` (×1) actually occurs for this VBO name | **NO — none of the 3 keys ever match** |
| `MS Outlook Extended VBO` | `Get Received Items`, `Mark Email As Read`, `Move Email` | only `Get Received Items (Basic) - Group Email` (×1) actually occurs | **NO — none of the 3 keys ever match** (the real string is a superset, but the router does exact `dict` membership, not substring, so it doesn't match) |
| `Utility_Object_Generic_ScreenShot` | `Take Screenshot` | `Capture Screenshot` (×1) | **NO — never matches** |

Net: of the 10 non-fusion `method_actions` dict entries this task added/rewrote across these 4
VBOs, only **1** (`Get Worksheet As Collection`) actually resolves against any real stage in the
one ground-truth sample this pipeline targets. `src/flowsmith/mapper/vbo_router.py::route()` does
exact `if method_name in entry.method_actions` dict-key lookup (line 126) — no substring or
fuzzy matching is applied to `method_actions` (only `method_patterns` gets a case-insensitive
*equality* check, and even that has no functional effect on confidence or template resolution,
confirmed by reading the surrounding code, lines 130–146). This is the same "task premise doesn't
match the real BP XML" bug class the first review already caught once for `PID_0005`'s `vbo_name`
— but here it recurs at the *method-name* level, across nearly every method-level addition this
task made, and went undetected by both prior reviews because neither checked method-level
`action=` strings against the real sample, only the `vbo_name`-level ones (and, for Outlook, only
the *content* of the templates, not whether their dict keys could ever be reached).

**Why this doesn't fail today's tests:** `resolved_action_template` (the field these `method_actions`
lookups populate) is produced by the router but is not read anywhere else in the codebase (`grep -rn
resolved_action_template src/flowsmith` → only the two lines in `vbo_router.py` that set the field;
zero consumers). It also has no effect on `confidence`/`band` (confirmed by live routing runs above
— confidence stays at `entry.confidence_base` regardless of whether a method match is found). So no
current test can catch this, and no currently-generated output is affected. This is exactly the kind
of latent, currently-invisible defect the coordinator asked this pass to hunt for: it will silently
produce empty/missing action templates the moment a future generator task starts consuming
`resolved_action_template`, unless corrected first.

  not a fault in the catalogue content itself — but it means half of this task's fusion-pattern

## Most significant gaps

1. **The large majority of this task's `method_actions` content is unreachable against the real
   sample due to method-name-string mismatches, not template-content errors.** 9 of 10 non-fusion
   entries added/touched by this task (`MS Excel VBO`'s `Write to cell`/`Save As`; both Outlook
   Extended VBOs' 3 keys each; `Utility_Object_Generic_ScreenShot`'s `Take Screenshot`) use method
   names that never appear as the literal `action="..."` value for any real stage calling that VBO
   in `samples/blueprism/PID_0171.bprelease` — confirmed by direct grep and by live-routing every
   real stage through `VBORouter.route()`. This is currently invisible (no test exercises
   `resolved_action_template`, and it has no effect on confidence scoring), but will silently
   produce missing/wrong action output the moment a future generator task consumes this field.
   Recommend the coordinator require this be re-verified against the real sample's actual
   `action=` strings before this data is trusted by a downstream task, or that the router be
   changed to fall back to `method_patterns` substring matching before shipping.
2. **`Close Workbook` + `Close Instance` fusion pattern is unreachable against real data.** The
   catalogue entry is correctly written and cited, but `_detect_vbo_call_fusions`'s numeric
   output→input handoff precondition never holds for this idiom's actual shape (both stages
   independently consume `handle` as an input; there's no output chaining between them). This is a
   cross-task (1b/2b) integration gap, not purely a 2b content defect, but it means the task's own
   step 6 second bullet doesn't function end-to-end today. The `Create Instance`+`Open Workbook`
   fusion, by contrast, is confirmed working end-to-end against real data.

   related to (but not the same string as) the `Utility - Image Search` entry this task's step 4
   named — was never added, and resolves as an unmapped/unknown VBO for all 4 real stages that call
