# Review: Task 5b — 2026-08-31 (rebuild cycle, commit `109a7e6`)

**Overall: 12%**

This is the 7th review of Task 5b overall, and the 1st review of the **rebuild** cycle after the
previous cycle's working implementation (certified 78% in `docs/reviews/5b-2026-08-31-fifthfixpass.md`,
"6th implementation cycle") was destroyed by an uncommitted `git checkout` during that review and
had to be rebuilt from scratch. The rebuild is a severe regression from the certified baseline, not

## Headline finding: `_build_variable_name_mapping` is a no-op against the real annotator, and the `SetVariable` render branch corrupts every DATA-stage declaration

`_build_variable_name_mapping` (`src/flowsmith/generator/pad.py:1042-1100`) looks up the PAD name
for each DATA/COLLECTION-stage data item via:

```python
pad_name = stage.pa_annotation.params_map.get(data_item.name, data_item.name)
```

i.e. it expects `params_map` to be keyed by the BP data item's own name (e.g.
`params_map["Retry Count"] == "num_retryCount"`). The **real** annotator
(`src/flowsmith/engine/annotator.py:239-243`, `_annotate_data`) never produces that shape — it
always emits a fixed 3-key dict: `{"variable_name": stage.name, "variable_type": ..., "initial_value":
...}`. So `.get(data_item.name, data_item.name)` always misses and falls back to the identity
mapping — `_build_variable_name_mapping` returns `{bp_name.lower(): bp_name}` for every real DATA/
COLLECTION stage in the corpus. No `num_`/`txt_`/`dtb_`/`bool_` prefix is ever produced by this
function against real data.

Separately, `_render_stage`'s `SetVariable` branch (`pad.py:1311-1351`) does:

```python
target_var_name = next(iter(annotation.params_map.keys()), stage.name)
bp_expr = next(iter(annotation.params_map.values()), "")
```

This works for `CALCULATION` stages (whose `params_map` really is `{target: expr}`), but for DATA
stages it grabs the **literal string `"variable_name"`** as the target (the annotator's fixed dict
key, not the real variable name) and `stage.name` (e.g. `"Retry Limit"`) as the "expression" — i.e.
every DATA-stage declaration in the corpus renders as `SET variable_name TO Retry Limit`.

**This is corroborated multiple independent ways, all against commit `109a7e6`:**

- Direct call to `PADGenerator().generate_process(...)` (the exact call the e2e suite's own fixture
  uses, `tests/e2e/test_pid171_pipeline.py:45`) against `samples/blueprism/PID_0171.bprelease`:
  `grep -c "SET variable_name TO"` → **148** occurrences in the Performer file, **29** in the Loader
  file (177 total). That is **78–79% of every `SET ... TO ...` line in both files** (148/188 and
  29/39 respectively).
- The full CLI pipeline (`uv run flowsmith convert --input samples/blueprism/PID_0171.bprelease
  --output outputs/review_5b_cli`) completes without error and produces a well-formed `.zip`, but the
  packaged `customizations.xml` inside it contains the identical **29** `"SET variable_name TO"`
  occurrences (spot-checked; e.g. `SET variable_name TO Item ID`, `SET variable_name TO Item
  Status`) — confirming this is not an artifact of a bespoke review script, it is what the tool
  actually ships.
- Even the `SET` lines that avoid the `"variable_name"` placeholder are unmapped: `SET Item Data TO
  DataTable.Create()`, `SET Get_Next_Item TO ""`, `SET Mail Items TO DataTable.Create()` — none of
  40 sampled non-placeholder `SET` lines carry a `num_`/`txt_`/`dtb_`/`bool_` prefix. Corpus-wide:
  **`grep -c "num_"` → 0 in both files. `grep -c "dtb_"` → 0 in both files.** The §A4 naming-prefix
  scheme this task exists to implement is not visible anywhere in the real regenerated output.
- **`FinalProduct_Collection` — the exact flagship variable the previous (destroyed) cycle certified
  at "27/0, done-when bar met" — has regressed to 0 correctly-mapped occurrences and only 4 raw,
  unprefixed occurrences** (`SET FinalProduct_Collection TO DataTable.Create()` ×3, plus one
  `@INPUT FinalProduct_Collection` line), all from the same unmapped `CreateNewDataTable`/DATA-stage
  paths. `dtb_finalproductCollection` appears **0** times anywhere.
- **`Consecutive Exception Count/Limit`** — same bug: `SET variable_name TO Consecutive Exception
  Count`, `SET variable_name TO Consecutive Exception Limit`.
- **`Retry Count/Limit` + siblings (`Close Retry`, `Enter Values_Retry`)** — same bug throughout:
  `SET variable_name TO Retry Limit`, `SET variable_name TO Close Retry Count`, `SET variable_name
  TO Enter Values_Retry Limit`, etc. `num_retryCount`/`num_retryLimit` (the previously-certified
  spelling): **0** occurrences anywhere.

All three of the task's named flagship variable families — the specific bar this task's lineage has
been scored against for 6 prior cycles — are now broken in the real corpus, not merely unverified.

## Why the 8 new unit tests didn't catch this

Every DATA-stage fixture in the 8 new tests (e.g.
`test_build_variable_name_mapping_scans_data_stages`,
`test_split_shape_with_mapping_preserves_variable_consistency`) constructs
`make_annotated_stage(..., params_map={"Retry Count": "num_retryCount"}, ...)` — a **fabricated**
`params_map` shape keyed by the BP data item's own name. That is not the shape the real annotator
(`_annotate_data`) ever produces (`{"variable_name": ..., "variable_type": ..., "initial_value":
...}`); it is exactly the shape `_build_variable_name_mapping`'s lookup line *expects*, so the tests
pass by construction against a fixture that was shaped to match the code under test rather than the
real upstream producer of that data. This is the same pattern flagged in every prior review of this
task (`docs/reviews/5b-2026-08-31-fifthfixpass.md`'s "sixth consecutive cycle... a new test passes
by construction while not actually exercising the code path it claims to guard") — this rebuild
makes it a seventh occurrence, and this time the consequence is not a maintainability nit but a
corpus-wide functional collapse.

One narrow positive: the specific argument-order bug in the 6th cycle's
`test_split_shape_with_direct_split_page_call` (binding `mapping` to the wrong positional parameter)
does **not** recur here — this rebuild's `_split_page_into_functions(page, process, shape_info,
process_map, variable_name_mapping)` has a different signature and the new
`test_split_shape_with_mapping_preserves_variable_consistency` calls it with arguments in the
correct positions. That one specific loose end from the destroyed cycle is fixed; it is a minor
positive next to the new defect's severity.

## Non-determinism (`id(match)`) — confirmed present in the code, empirically **not observed** in this corpus (because the path never fires)

`pad.py:1181`/`1195` (`temp_var = f"txt_trimmed_{id(match)}"` / `f"txt_lowered_{id(match)}"`) is
confirmed present exactly as described. Two independent full regenerations of the real solution
(`outputs/review_5b_run1`, `outputs/review_5b_run2`, via identical direct
`PADGenerator().generate_process()` calls in separate `uv run python` processes) produced
byte-identical output (`sha256sum` match on both `.robin` files). **This does not vindicate the
design** — it happened to be identical here only because **the `Trim`/`Lower` translation path is
never reached for real `PID_0171` data at all**: `grep -c "txt_trimmed_\|txt_lowered_\|Text.Trim\|
Text.ChangeCase"` → **0** in both files, despite the raw BP source containing genuine `Trim(`/
`Lower(` calls in 18 `Calculation`, 6 `MultipleCalculation`, and 39 `Decision` stages across the
whole `.bprelease` (confirmed via direct XML grep, e.g. `Trim([Random Number])` on the "Trim" stage
of the "Download File from Azure" page). Cross-referencing against
`mapping/page_target_map.yaml`, none of the 18 pages currently in the consolidated Loader/Performer
`FUNCTION` output contain a `Trim`/`Lower`-bearing `Calculation`/`Decision` stage — the one page that
does (`ConvertConfigFile As Collection - Copy`) is explicitly folded into the Cloud Flow tier (out
of `pad.py`'s Desktop Flow scope), and the "Download File from Azure" page that contains the `Trim`
stage above isn't in `page_target_map.yaml` at all, so it never renders. **The `id(match)` defect is
real and remains a first-class violation of this project's offline/deterministic constraint for any
of the ~199 other automations (or any future PID_171 page addition) whose `Calculation`/`Decision`
stages do use `Trim`/`Lower` and do get routed into the rendered subset** — it is simply dormant for
this specific corpus's currently-in-scope pages, not fixed and not disproven as a live risk.

## Most significant gaps

- **[Blocking] `_build_variable_name_mapping` never matches the real annotator's DATA-stage
  `params_map` shape, so it returns an identity mapping for every DATA/COLLECTION-declared BP data
  item in the corpus.** Fix: read `stage.pa_annotation.params_map["variable_name"]`/`["variable_type"]`
  (the real keys `_annotate_data` emits) to derive the prefix, not `.get(data_item.name, ...)`.
- **[Blocking] `_render_stage`'s `SetVariable` branch treats every stage's `params_map` as if it had
  the `CALCULATION` shape (`{target: expr}`), corrupting every DATA-stage render into `SET
  variable_name TO <raw BP name>`.** Fix: branch on `stage.stage_type` (or on whether `"variable_name"`
  is a literal key in `params_map`) before deciding how to extract target/value, and route DATA
  stages through their own dedicated rendering (as the destroyed cycle 6 apparently did, per that
  review's note that "DATA stages pull their type from the stage's own `PAAnnotation.params_map`,
  not the process-wide `variable_name_mapping`" via "a completely separate, mapping-independent code
  path").
- **[Blocking] All 3 of the task's own flagship-variable checks (`FinalProduct_Collection`,
  `Consecutive Exception Count/Limit`, `Retry Count/Limit`+siblings) have regressed from a certified
  fully-consistent state to broken in the real corpus.** This is exactly the corpus-level
  verification the task's own history has repeatedly needed and the implementer's summary explicitly
  flagged as not having been done this cycle — that flag was correct and this review confirms the
  concern it named was real.
- **The 8 new unit tests all construct a fabricated DATA-stage `params_map` shape that doesn't match
  what the real annotator produces**, so none of them could have caught (and none did catch) the
  corpus-breaking bug above. This is the seventh consecutive cycle in this task's history where a
  new test passes by construction against a fixture shaped to match the code under test rather than
  its real upstream producer.
- **`id(match)`-based temp variable naming (`pad.py:1181`, `1195`) remains a live, un-vindicated
  determinism risk.** Confirmed present in code; confirmed *not currently triggered* by the real
  `PID_0171` corpus (0 real invocations, for reasons unrelated to any fix — the relevant pages are
  simply out of the currently-rendered subset). Should still be replaced with a stable, deterministic
  name (e.g. a per-expression counter or a hash of the match text/position) before any corpus is
  regenerated that does route a `Trim`/`Lower` call through a rendered page.
- Do-step 2 (`Trim`/`Lower` → separate action lines) has real code and passing isolated unit tests
  but has **never once been exercised against real `PID_0171` output** across any cycle of this
  task, including this one — the summary's own candor about this ("No real-corpus verification…")
  should be treated as a standing methodology requirement for closing this task, not a one-off
  omission.

## Verdict

**Needs another implementation pass — this is a regression, not a fix-pass-away-from-done state.**
The rebuild's own stated goals (Do-step 2, the two named loose ends from the destroyed cycle) are
mostly addressed on their own narrow terms, but the rebuild introduced a corpus-wide functional
regression in exactly the mechanism (`_build_variable_name_mapping` / DATA-stage rendering) that the
destroyed cycle 6 had gotten right, and none of the 8 new tests would have caught it because they
test against a fixture shape that doesn't match the real annotator. The next implementation pass
must (1) fix the DATA-stage `params_map`-shape mismatch in `_build_variable_name_mapping` and the
`SetVariable` branch's stage-type-blind key/value extraction, (2) re-verify against the real
regenerated corpus (not just unit tests) that all 3 flagship variable families are restored to the
previously-certified consistent state, and (3) replace the `id(match)` temp-variable naming with a
deterministic scheme before this is considered safe for the other ~199 automations in this program.
