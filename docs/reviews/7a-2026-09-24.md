## Most significant gaps

1. **`txt_WorkQueueId` is a dangling reference, so the "citation-backed" claim is only half true.**
   `pad.py:1571-1574` substitutes it, and the commit message cites reference L150 and L1371. L1371
   is the call-site form. L150 is the *assignment* (`SET txt_WorkQueueId TO
   obj_Config['Ctrl_WorkQueueId']`), and it lives inside reference `FUNCTION 'Load Config Data'
   GLOBAL` (L118). No `Load Config Data` function exists in the generated output (Task 7d item 3).
   Neither generated `.robin` contains any `SET txt_WorkQueueId` or `Ctrl_WorkQueueId`; the only
   occurrences are the two call sites at Performer L165/L345. Also, 7d item 3 as written only adds
   a mapping entry. Translating the BP page will not naturally produce this assignment, because BP
   reads `ConfigFileData.Queue Name`, not a `Ctrl_WorkQueueId` key. **No task currently owns
   producing the declaration.** Either 7a should flag the binding with a `# VERIFY`/`# TODO` naming
   the unmet dependency, or the coordinator should assign the assignment to 7d item 3 explicitly.
2. **The binding trigger is an uncited, PID-specific heuristic hardcoded in Python.**
   `if "ConfigFileData.Queue Name" in queue_name:` (`pad.py:1571`) matches one BP data-item name
   from this process. No doc cites it, and it breaks CLAUDE.md's rule that "YAML mapping config
   lives in mapping/ — never hardcode mappings in Python". It doesn't even cover all of PID_0171:
   the `Get Next Item` on page `Mark leftout Items as Exception` takes `'[Queue Name]'` (from
   `ast.json`). If that page is ever rendered, it falls through to `_translate_bp_expression` and
   binds a queue *name* where PAD's `WorkQueue:` takes an *ID*. For the other ~199 automations in
   the program, any other config-item naming falls straight back to the dotted-expression path
   that the 09-04 review rejected.
3. **The tests still can't catch the queue-binding defect class.** The remediation plan's Sub-Task
   3 items 2-3 ("assert the `Get Next Item` queue expression is canonical…", "assert…references
   correspond to declared/canonical variables") were not implemented.
   `test_work_queues_placeholders_are_substituted` (test_pad.py L2626-2637) only asserts
   `"WorkQueue: <id>" not in line` and `"WorkQueue:" in line`, and its comments still describe the
   old `dtb_ConfigFileData` behaviour. Reverting to `dtb_ConfigFileData.Queue Name`, or leaving
   `txt_WorkQueueId` undeclared, would both pass. The 09-05 review's statement that "all four
   sub-tasks … have been met" is incorrect on this point.
4. **The `Tag Item`/`Defer` fallback invents a variable and doesn't say why it stopped.** The
   `else` branch of `templates/pad/actions/work_queues.robin.j2` emits `# TODO: WorkQueues.Tag Item
   — complete this action block` followed by `SET Tag_Item TO ""` (Performer L346-347, 493-494,
   503-504, 507-508). The TODO doesn't cite the mapping table's STOP reason (vbo-action-mapping.md
   L32), and the `SET` line creates an unprefixed variable with no BP counterpart. The template's
   other branches (`WorkQueues.CreateQueue(...)`, `WorkQueues.AddQueueItem(...)`, etc.) are also
   uncited made-up syntax, though none of them is reached for PID_0171. Strictly, the template
   file is outside 7a's declared file scope; route this to 7d item 4 (fallback honesty) or a 7a
   follow-up with widened scope.
5. **`Update Status` literals use uncited double-quote syntax** (`ProcessingNotes: "COMPLETED"`,
   Performer L249/472/574/696/858). The reference uses `$'''...'''`/`'...'`. The raw BP literal is
   passed through `_translate_bp_expression` unchanged, so the root cause is the shared translator
   (Task 5b territory), but it shows up on 7a's rendered lines.
6. **The Mark Exception variant hand-off to 7b is not recorded in 7b's task section**
   (task-prompts L1186-1195). The coordinator should add one line there so the three catalogued
   variants are actually used.
7. **Observations, outside 7a's written scope and not scored:**
   (a) The Loader's `Is Item In Queue`/`Add To Queue` (Loader L183/L190) are still `# TODO` stubs,
   even though the same Work Queues table has cited templates for them (Loader L90-102, L140).
   Task 7a's *Do* list only named 4 actions, so this is a task-scoping gap.
   (b) The catalogue's `method_patterns` (L426-438) are still PID_0127-era names (`Create Queue
   Item`, `Set Item Tags`, `Defer Queue Item`, …) rather than PID_171's real BP method names (`Add
   To Queue`, `Tag Item`, `Defer`, `Update Status`, `Is Item In Queue`).
   (c) `Get Next Item` renders as a standalone statement (L165, L345) rather than as the `LOOP
   WHILE (...)` condition the mapping table says it drives (reference L1371). That's a loop
   structure issue for the control-flow tasks, not 7a.
