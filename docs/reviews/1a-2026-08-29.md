## Most significant gaps

- **The task's literal "Done when" scenario is fully met and independently verified** — this is not in question. `parser/process.py` now correctly extracts ACTION `<outputs>` into `data_items` (additive to `params_map`, confirmed via `test_action_input_in_params_map` still asserting the pre-existing `params_map` shape), and `<onsuccess>`/`<ontrue>`/`<onfalse>` targets are captured as plain stage-ID strings with no graph traversal or Block→Recover construction added (confirmed: no `Block`/`Recover`/reachability logic appears anywhere in the diff to `parser/process.py` or `ast/builder.py`; `_detect_vbo_call_fusions` itself was correctly left untouched, matching the task's explicit out-of-scope instruction).
- **Only one of the two real fusion pairs named in the task's own motivating context (`docs/reviews/1b-2026-08-29.md`, §B_FUSION) is actually unblocked.** `Create Instance`→`Open Excel` now fuses correctly end-to-end against the real sample (verified independently with a synthetic router). `Close Workbook`→`Close Instance` still does not, because that pair's real BP XML has no `<outputs>` on either stage — the "same handle-chaining shape" claim in architecture doc §B_FUSION is not accurate at the structural level Task 1b's detector implements. This needs either (a) a correction to §B_FUSION's characterization of the close-side pair, or (b) an extension to Task 1b's structural signal to also recognize "two adjacent same-VBO stages both referencing the same upstream-set variable by name," which is a materially different (and weaker) signal than "output feeds next stage's input." Flagging this now since it will otherwise resurface as a silent gap when Task 1b is re-run/re-scored.
- **One implementer-added test creates false confidence about the above gap**: `test_fusion_second_excel_pair_close_resolves` (`tests/ast/test_builder.py` L831-905) fabricates an `is_output=True` on `Close Workbook`'s `handle` data item that does not exist in the real XML, and thus "passes" while telling a story the real pipeline cannot reproduce. This is exactly the "synthetic fixture masking a real-sample gap" anti-pattern the prior Task 1b review (and this project's core discipline) called out — it recurred here despite the explicit lesson from that review.
- **Minor reporting inaccuracy**: the implementer's summary claims "15 new tests" for `tests/parser/test_process.py" and "10 new tests" for `tests/ast/test_builder.py`. Actual counts from the diff: 11 new test functions (+4 new fixtures, likely miscounted as tests) in `test_process.py`, and 11 new test functions (not 10) in `test_builder.py`. Immaterial to functionality, but consistent with this session's recurring pattern of imprecise self-reporting from this role.
- `tests/ast/test_models.py` was listed in the task's declared file scope but not touched — not a functional gap (the new `BPStage` fields are exercised via `test_builder.py`'s threading tests), but worth noting for completeness.

pass — with a flagged follow-up.
