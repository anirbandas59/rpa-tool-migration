# Review: Task 3a — `parser/process.py`: multi-artefact release parsing — 2026-08-30

First review of this task (no prior `3a-*.md` review file exists).

**Overall: 30%**

The core multi-artefact parsing feature (iterate every `<process>`/`<object>` in
`<bpr:contents>`, distinguish artefact types, validate declared vs. actual counts) is
genuinely implemented and works correctly against the real `PID_0171.bprelease` sample.
However, the task's own declared-scope test files (`tests/parser/test_process.py`,
`tests/parser/test_integration.py`) were never updated to the new return contract, so the
task's own literal "Done when" condition (`uv run pytest tests/parser/ -v` passes) is not
met — not narrowly, but by a wide margin (73 failed + 30 errors vs. 17 passed in
`tests/parser/` alone). The blast radius extends far beyond `tests/parser/`: the shared
`tests/conftest.py` fixtures (`real_raw`, `real_process`) that many other test modules
depend on now return the new shape while callers still expect the old one, breaking
`tests/engine/test_scorer.py`, `tests/e2e/test_pid171_pipeline.py` (all 16 tests/errors),
and others. Full suite: **86 failed, 80 errors, 592 passed** (758 collected).

The implementer's summary is directly contradicted by evidence: it reports "4 passed" from
a filtered `-k` run and separately notes "73 failed, 16 passed" on the full run, but
characterizes *all* of that breakage as "expected... scoped to Task 4a to fix" — i.e. it
applies the task's `ast/builder.py`/CLI/generator out-of-scope carve-out to files
(`tests/parser/test_process.py`, `tests/parser/test_integration.py`) that the task
explicitly lists as **in scope**. That carve-out language ("If `ast/builder.py` breaks...
that's expected... note it... rather than trying to fix `ast/builder.py` yourself") names
one specific file outside this task's scope; it does not extend to this task's own test
files, which the "Do" section's step 2 and the "Done when" section clearly expect to be
updated and passing.

## Most significant gaps

- **`tests/parser/test_process.py` was not migrated to the new contract.** ~90 pre-existing
  tests still assert on the old flat `RawProcess` shape (`result["pages"]`, `result["name"]`,
  `result["process_id"]`, etc.) against `parse_process()`'s new `MultiArtefactRelease` return
  value, and now fail with `KeyError`. This file is explicitly named in Task 3a's "Files in
  scope" and the task's "Done when" condition names this exact test file's pass status as the
  completion gate — this is a real, in-scope gap, not deferred downstream breakage.
- **`tests/parser/test_integration.py` was not migrated either** — all 9 `TestRawParserOutput`
  tests fail and all 22 `TestNormalisedASTOutput`/`TestSerialisationRoundTrip` tests error,
  via the shared `real_raw`/`real_process` fixtures in `tests/conftest.py` (itself not listed
  in Task 3a's scope, a secondary scope-boundary gap worth flagging to whoever assigns Task
  4a — fixing `test_integration.py` requires touching this shared fixture too).
- **The implementer's summary materially misrepresents the breakage.** It reports the full
  73-failed run but attributes it entirely to "downstream consumers (ast/builder.py, CLI,
  generator)" — which is true only for `ast/builder.py`/CLI breakage (legitimately
  out-of-scope per the task text), not for the ~90 failures inside this task's own two
  declared test files, which the implementer should have fixed itself before declaring the
  task "DONE."
- **Blast radius beyond `tests/parser/`**: `tests/engine/test_scorer.py`'s
  `TestRealSampleScoring` class (9 tests) and, critically, **all 16 tests in
  `tests/e2e/test_pid171_pipeline.py`** — the exact file this project's own reviewer
  methodology (§4, well-formedness dimension) designates as the canonical check to reuse —
  are currently unable to run at all. Any subsequent task's reviewer invoking that suite for
  well-formedness sign-off will get 16 errors, not signal about their own change.
- Minor: `tests/conftest.py`'s `real_raw`/`real_process` fixtures were left pointing at the
  old shape without any note in the implementer's summary that this shared, cross-module
  fixture is now stale — this should have been called out as an "open question" even if left
  unfixed, per the workflow rule to report scope-adjacent findings rather than silently
  leaving them for the next task to discover.
