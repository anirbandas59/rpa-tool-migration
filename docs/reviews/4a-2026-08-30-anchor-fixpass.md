# Review: Task 4a — `ast/builder.py`: call-graph/reachability model — anchor fix pass — 2026-08-30

This is a re-review of the anchor-edge + annotator fix pass that followed
`docs/reviews/4a-2026-08-30-fixpass.md` (40%, "needs another implementation pass"). That review's
central finding was: dropping `Anchor` stages without collapsing their pass-through `onsuccess`
edge broke the BFS at ~13% of all edges, causing 12 of 24 pages to be wrongly marked unreachable,
and `engine/annotator.py` was never updated for `is_process_call`. This pass explicitly targeted
both. Verification below confirms the Anchor pass-through mechanism and the annotator wiring are
both genuinely, correctly implemented and independently reproducible. But it also finds that the
reachability model is **still wrong for the same order of magnitude of pages** (9 of 24, not
counting 2 confirmed orphans) as before, via **two root causes the implementer's summary does not
correctly or completely account for**: (1) the SubSheet name-mismatch explanation given is real for
only 4 of the 9 pages, and is characterised as blocked on unavailable `processid` data when that
data in fact exists in the raw BP XML and simply isn't parsed yet (a mischaracterisation of the
gap's nature, not just its scope); and (2) a wholly undisclosed second defect — the implicit
Block→Recover reconstruction (this task's own Do-step 2) never fires for the real `Block` stage

flow node) — silences the entire exception-handling branch (`Send mail`, `Mark Item As Exception`,

`Note` was left out even though it needs the identical pass-through-edge collapse as `Anchor`; 20

## Verification performed

### 1. Anchor pass-through correctness (multi-hop chains, no incorrect new edges)

Read `_build_anchor_passthrough_map`/`_apply_anchor_passthroughs` directly
(`src/flowsmith/ast/builder.py` lines 564-629). The map-building loop follows `onsuccess_target`
through a `while current_id and current_id not in visited` chain with a `visited` set for cycle
safety, and only records a mapping once a non-`Anchor` target is found — this correctly handles
N-hop Anchor chains, not just single-hop. `_apply_anchor_passthroughs` only rewrites
`onsuccess_target`/`ontrue_target`/`onfalse_target` when the current value is a key in the map,
so it cannot fabricate an edge that wasn't already present. Independently re-ran the real sample:
reachable pages went from 10→13 of 24 (previous fix pass's own baseline was 10 reachable), a real,
verified improvement, not just a claimed one.

### 2. The "9 false-unreachable pages are all SubSheet name-matching" claim — only partially true

Independently reproduced the current output: 24 total pages, 13 reachable, 11 unreachable. The 2
named orphans (`Mark leftout Items as Exception`, `Send Info to Data Gateways`) are correctly
unreachable; `Get Mails`/`Populate Queue` are correctly reachable — the task's own literal
Done-when passes.

Of the other 9 unreachable pages, checked each directly against the raw `PID_0171.bprelease` XML
(not just the AST) for real callers:

- **4 pages — SubSheet name-mismatch is real and confirmed** (`Read Input Data From Excel`,
  `ConvertConfigFile As Collection - Copy`, `Send mail - No New Mail`, plus cascade
  `Read Excel As Collection`): each has exactly one real `<processid>`-bearing `SubSheet` stage
  pointing at it, but the calling stage's own `name` attribute doesn't match the target page's
  name (e.g. `Get Input Data from Excel ` (trailing space) calls `processid=8f814e4a-...` which is
  `Read Input Data From Excel`'s own `subsheetid` — an exact, verified `processid` match that the
  current name-based lookup can't find). **Critically: `processid` is present in the raw XML on
  every real `SubSheet` stage checked** (`<processid>8f814e4a-...</processid>` etc.) — it is not
  "data that doesn't exist yet," it is data the parser (`parser/process.py`, outside this task's
  declared file scope) simply doesn't capture into `RawStage` yet. The implementer's summary
  characterises this as "processid-based resolution isn't available... a parser gap, cited as
  outside this task's scope," which is directionally correct about the *file scope* boundary but
  materially wrong about *why* — it's a one-field parser omission, not a genuinely unavailable
  upstream fact. This distinction matters for how the coordinator should prioritise the follow-up.
- **1 page (`Close Down`) has zero callers anywhere in the raw XML** — no `<processid>` reference,
  no `SubSheet`-type stage with a matching or mismatching name, nothing. This does not fit the
  implementer's "name-mismatch" bucket at all. It may be a third real orphan the architecture
  doc's §B14 table didn't catch (the doc's own methodology explicitly verified orphan status via
  `<processid>` search only for the two flagged rows, #16/#21 — row #18 `Close Down`'s
  "Performer → `Close Application`" mapping is asserted without a cited caller-verification,
  unlike row #14's `Completed No Outcome`, which the doc explicitly confirms via caller count).
  Not a defect in this task's code — if genuinely uncalled, marking it unreachable is *correct* —
  but it should be flagged back to whoever owns architecture doc §B14 rather than silently absorbed
  into "SubSheet name-matching limitations."
- **4 pages — traced to a wholly different, undisclosed root cause**: `Send mail`,
  `Mark Item As Exception`, `Mark as read and move to exception folder` (which also independently
  has a real name mismatch — `Mark as read mail and move Exception Folder` vs.
  `Mark as read and move to exception folder` — so it needs *both* fixes), and cascade
  `Completed No Outcome`. See the Error-handling row above: these all live behind the
  `Recover20`/`Resume1` implicit-exception chain that the Block→Recover reconstruction never
  reaches, because the real `Work` Block it should pair with has no independent incoming edge.
  This was not mentioned anywhere in the implementer's summary, which attributed all 9 pages to
  the single name-matching cause.

### 6. Dangling-reference scan (well-formedness, per strategy doc §4.6)

Built the real PID_0171 AST and checked every `onsuccess_target`/`ontrue_target`/`onfalse_target`
against the full set of stage IDs present across all pages. Found **29 dangling targets** — edges
that point at a stage ID no longer present anywhere in the AST post-normalisation. Cross-referenced
each dangling target's raw (pre-normalisation) stage type: **20 are `MultipleCalculation`** (a
pre-existing collapse rule that renames one raw `stage_id` into N `{id}__calc_{i}` sub-stage IDs
without leaving any redirect for whatever pointed at the original ID — this predates this session,
likely from the original AST builder or Task 1a, and is outside this pass's own diff, but it
directly undermines the "follow `onsuccess`/`ontrue`/`onfalse` edges" premise this task's Do-step 1
depends on, and was not caught or disclosed by this task at any point in its history); **8 are
`Note`** (squarely this pass's own remit — `Note`, like `Anchor`, is a CLAUDE.md skip type that can
carry a pass-through `onsuccess` edge in real BP data, confirmed directly: `Note9`,
"No more items available", has `<onsuccess>f3538934-...</onsuccess>`, exactly the same pattern the
Anchor fix was built to collapse, but `_build_anchor_passthrough_map` only checks
`stage_type in ("Anchor",)`, not the full skip-type set). In this specific sample the one traced
Note case (`Delete Input File` → `Note9`) happens not to change any page's reachability outcome
(the target it should redirect to, `f3538934-...`, is already reached via another path) — but the
mechanism is incomplete on its own terms, and the 20 `MultipleCalculation` cases are not similarly
neutral (one of them, `Recover20` → `Exception Data`, sits directly on the broken exception-handling
chain from finding #2 above — even a corrected Block→Recover reconstruction would immediately
dead-end one hop later on this dangling reference).

## Most significant gaps

- **The Block→Recover implicit-edge reconstruction (Do-step 2) still doesn't work for the one case
  that matters in real data** — a Block stage with no independent incoming edge (the normal case
  for a real try/catch wrapper, where the "try" body's protected stages are entered directly by the
  mainline flow and only the exception path is implicit) never gets its paired Recover visited,
  silencing 4 of 24 pages' worth of genuine, functioning BP error-handling logic that architecture
  doc §B15 confirms should have a PAD equivalent. This is a new, more precise diagnosis of the same
  Do-step 2 gap flagged (differently) in the prior review, and it was not found or disclosed by the
  implementer this pass.
- **The implementer's "9 false-unreachable pages = SubSheet name-matching" explanation is materially
  incomplete**: only 4 of 9 fit that bucket cleanly, 1 doesn't fit either disclosed cause
  (`Close Down`, likely a third real orphan the architecture doc never verified), and 4 trace to the
  undisclosed Block→Recover gap above (one of which needs *both* fixes). The characterisation of
  `processid` as data that "isn't available" is also inaccurate — it exists in the raw XML on every
  real `SubSheet` stage checked; it's simply not captured by `parser/process.py` yet, a fixable
  one-field gap in a file outside this task's own scope, not a fundamentally missing upstream fact.
- **29 dangling `onsuccess`/`ontrue`/`onfalse` references remain in the real AST** — 8 from this
  pass's own incomplete skip-type handling (`Note` needs the identical pass-through-edge collapse
  this pass built for `Anchor`, but wasn't given it), 20 from a pre-existing `MultipleCalculation`
  ID-collapse defect that silently orphans edges pointing at the original stage ID. "No dangling
  references" is one of the three explicit checks the strategy doc names for this dimension, and it
  fails; this was not caught by the implementer or by the previous review.
- **No dedicated unit test exists for the Anchor pass-through mechanism itself** — only the
  (still-incomplete) real-sample reachability assertions exercise it indirectly.
- Process discipline is otherwise improved: no undisclosed new test failures this time (a genuine
  fix of the prior pass's most-repeated criticism), all disclosed claims (Anchor multi-hop
  correctness, hardcoded counts, annotator wiring) verified true on direct inspection, and the
  task's own literal Done-when passes. The gap is that the *disclosed* deviation ("SubSheet
  name-matching") is not the *complete* explanation for why the deliverable is still substantially
  wrong, and a full independent cross-check (as this review brief required) surfaces that the
  actual defect surface is broader and includes at least one genuinely new, in-scope class of bug
  (Block→Recover) plus a well-formedness violation (dangling references) neither party had found.

## Verdict

**Needs another implementation pass.** The two specific defects this pass targeted (Anchor
pass-through, `is_process_call` annotator wiring) are both genuinely, verifiably fixed, and process
discipline around test-failure disclosure has improved. But the task's actual deliverable — a
call-graph model that correctly distinguishes orphan pages from called ones — is still wrong for
9 of 24 real pages (37.5%), the same order of magnitude as before the fix pass, via a partially
different and only partially disclosed set of root causes. Recommend, in priority order: (1) fix
the Block→Recover reconstruction to trigger from any protected stage already reached inside a
Block's scope, not only from the Block stage's own independent BFS-reachability (this is squarely
Do-step 2's own unmet requirement); (2) extend the pass-through-edge collapse to the full skip-type
set (`Note`, not just `Anchor`); (3) escalate the `MultipleCalculation` ID-collapse dangling-edge
defect to the coordinator — it predates this task but blocks its premise and needs either a fix or
an explicit scope decision; (4) escalate `parser/process.py`'s missing `<processid>` capture as a
correctly-characterised (present-in-XML, one-field, low-risk) parser gap rather than an
unavailable-data limitation, so the coordinator can weigh a small out-of-scope parser change against
continuing to rely on fragile name-matching; (5) re-run reachability against the real sample after
(1)-(3) and confirm it approaches architecture doc §B14's ground truth (22 reachable / 2 confirmed
orphans, with `Close Down`'s status independently confirmed with the doc's owner); (6) add a direct
unit test for the Anchor/Note pass-through mechanism that doesn't depend on the real sample's
current, still-incomplete reachability outcome; (7) continue running and reporting the full suite
(not just the task's own scoped files) before the next "done" declaration — this pass happened to
be clean, but the practice of not checking was still not corrected.
