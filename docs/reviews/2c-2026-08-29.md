## The flagged "Process row" finding — verified genuine

Confirmed via `git diff -- mapping/stage_rules.yaml`. The pre-task `Process` row read:

```yaml
- bp_stage_type: Process
  canonical_type: ""
  pa_target_action: ""
  pa_module: "System"
  confidence_base: 0.0
  notes: >
    Process metadata root node. Appears once per process.
    SKIP — information already captured in BPProcess model header.
    Count in sample: 1.
```

This is a genuine, pre-existing bug: it describes `ProcessInfo`'s role (the metadata/skip marker —
the file already has a *separate*, correctly-labeled `ProcessInfo` row a few lines below with
near-identical wording), not `Process`'s actual role. `CLAUDE.md`'s own normalisation table is
unambiguous: `PROCESS → ACTION (is_process_call=True)`. The implementer's replacement row
(`canonical_type: ACTION`, `pa_target_action` describing the CALL-vs-Workflow ambiguity,
`confidence_base: 0.5`) is the correct fix, not a new error. Net row count: 26 (original) + 2 new
(`Alert`, `Skill`) = 28, not 26+3=29 — the task prompt's "3 missing … none present today" premise
was itself slightly wrong (`Process` existed but was mislabeled); the implementer's summary didn't
surface this nuance explicitly, but the coordinator's flag and my own `git diff` confirm the net
effect is correct and the file is not missing anything. This is a genuine, well-cited improvement,
not an accidental new error — nothing else in the `Process` row conflates it with any other type.

One caveat worth recording: the task text (and the implementer's note, which cites it) attributes
this special-case finding to `architecture doc §B13's "Process-call special case"`. I read all of
§B13 directly and that phrase/finding is **not** actually there — §B13 only points to
`docs/pad-reference/vbo-action-mapping.md` for VBO rows and says nothing about `Process`-type
stages. The real source is `docs/bp-to-pad-implementation-strategy-PID171.md` §2.3 (verified
verbatim: "BP's single Process-type stage in the main process … maps to Cloud_Main's Try: Init
scope → a Workflow-type action calling `CF_PID_171_US_Read Config File`"), which the implementer
also cited. So the underlying fact is correctly sourced and accurate; the "§B13" half of the
citation is inherited from an imprecise instruction in the task prompt itself, not fabricated by
the implementer. Also worth flagging: this directly conflicts with architecture doc §B9's own rule
("[the sibling process] is a call target whose logic gets inlined as steps within the caller … not
separately translated") — an unresolved tension between two doc sections that the task correctly
tells the implementer to punt on (`confidence_base: 0.5`, routing "needs a human/reviewer decision,
don't hardcode one"), which the row's `notes` field does, appropriately.
