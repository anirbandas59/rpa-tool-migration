## Scope-guard hook investigation (separate finding, not scored against Task 2a)

The implementer's claimed deviation — that it bypassed `Edit`/`Write` in favor of Bash because
`.claude/hooks/pre-hooks/guard_implementer_scope.py` "compares absolute paths ... against relative
paths ... and never matches, so the guard never actually blocks anything" — was investigated
directly by reading the hook and driving it with realistic payloads (not eyeballed).

**The claim is directionally right that there's a real path-format bug, but the specific mechanism
and consequence stated is backwards.** Verified with a controlled test harness invoking the hook
exactly as `PreToolUse` would for `Edit`/`Write` (whose `file_path` contract requires an **absolute**
path — confirmed in this environment's own tool description: "file_path must be an absolute
path"):

- An absolute Windows path for the genuinely in-scope file
  (`C:\Users\...\rpa-tool-migration\mapping\vbo_catalogue.yaml`) → hook exits **2 (blocked)**,
  reporting it as "outside Task 2a's declared file scope" — even though it is exactly the declared
  scope.
- An absolute path for a genuinely out-of-scope file → also exits 2 (blocked) — correctly, but for
  the wrong reason (path-format mismatch, not scope reasoning).
- A relative path (`mapping/vbo_catalogue.yaml`) — the only form the hook's `normpath`/`startswith`
  comparison can ever match — exits 0 (allowed). But `Edit`/`Write` never actually send relative
  paths, so this branch is dead in practice.

Root cause: the hook normalizes both sides with `os.path.normpath(...).replace("\\", "/")` but
never relativizes the (always-absolute) `tool_input.file_path` against `CLAUDE_PROJECT_DIR` before
comparing it to the scope file's relative entries. Exact-equality and `startswith(prefix + "/")`
can therefore never succeed against an absolute target.

**Net effect is the opposite of "never blocks":** the hook unconditionally blocks every `Edit`/
`Write` call the `pad-implementer` subagent makes, regardless of whether the target is genuinely
in scope or not, because `in_scope` evaluates `False` for every real absolute path it's ever given.
This is why the implementer says it fell back to Bash-based file edits — not because the guard was
silently permissive, but because it made `Edit`/`Write` completely unusable. The practical
consequence for the coordinator workflow is the same bottom line the task asked me to check
(scope enforcement has not actually been functioning as designed, for Task 1's passes too, since
this bug is structural and would reproduce on every task), but via a different and arguably worse
mechanism: it doesn't pass out-of-scope edits through `Edit`/`Write` unchecked — it forces every
implementer onto Bash, a tool this hook's `matcher: "Edit|Write"` does not cover at all, meaning
the actual edits made in practice have had **zero automated scope enforcement**, not "advisory
weakened" enforcement. This is worth a dedicated fix (relativize `target_path` against
`CLAUDE_PROJECT_DIR`/`os.getcwd()` before comparing, the same way `guard_reviewer_readonly.py`
sidesteps the issue with a substring check) independent of Task 2a's own scoring, and applies
retroactively to every prior task pass that reported using Bash "because the guard didn't seem to
work."
