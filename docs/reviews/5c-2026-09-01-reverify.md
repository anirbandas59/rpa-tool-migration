## Disagreement with the prior 2026-09-01 review — read this first

The prior review (`docs/reviews/5c-2026-09-01.md`) quotes the exact same output lines this review
does:
```
327: # System.IF <expr> THEN <true-branch> ELSE <false-branch> END # VERIFY: System Exception? (confidence 0.85)
328: END
329: LABEL 'Mark Item As Exception'
330: CALL 'Mark Exception'
331: LABEL 'Mark Item As Completed'
332: CALL 'Mark Complete'
```
and its "FUNCTION Functional Fidelity" section calls this "correct behavior, not a defect" because
both continuation stages are positioned outside the `BLOCK`. That check (position relative to the
`BLOCK`) is correct as far as it goes — but it stops one step short of tracing what actually
*executes*. Line 327 is a **comment** (`#`-prefixed) — the `Decision` stage that should have become
a real `IF flg_ErrorOccurred = True THEN GOTO ... END` gate was rendered as a confidence-stub
comment instead of code (a Task 5a/5b decision-stage-translation gap, not something Task 5c
introduced). `LABEL` statements in Robin syntax are not branches — they're fall-through no-ops.
With no functioning `IF`/skip-`GOTO` between them, execution reaches line 329, falls through it,
executes `CALL 'Mark Exception'` (330), falls through `LABEL 'Mark Item As Completed'` (331), and
executes `CALL 'Mark Complete'` (332) — unconditionally, on **every** loop iteration, success or
failure alike. This is confirmed by direct inspection of the regenerated file at
`outputs/generated/PID_0171/robin_review_5c/PID_171_US_Process_LIMS_Prelude_Performer.robin`
(same content this review and the prior one both worked from).

This matters because §A5's hard constraint has two halves, and Task 5c's own Do-step 2 restates
both: (1) no `IF` inside the handler body — satisfied; and (2) "any branching on what happened
belongs in a plain `IF` placed after the enclosing scope, checking a flag the handler set" — **not
satisfied**, because the implementation never synthesizes that `IF` itself; it assumes the generic
per-stage pipeline will supply it via whatever `Decision` stage originally sat between `BLOCK` and
`RECOVER`, which for this exact real page it does not (comment stub, not code). The task exists
specifically to get this one page's dispatch right, and for the literal worked example it is
generating a real correctness bug (every item double-marked Completed-and-Exception), not just a
stylistic deviation. That is why this review's score and verdict differ from the prior pass.

## Other gaps (secondary to the one above)

1. **Typed handler dispatch is dead code for every real `BLOCK` stage**, not merely "not exercised
   for this one Block" as the prior review characterized it. `stage.exception_type` is documented
   as populated only on `EXCEPTION` (throw) stages, never `BLOCK` stages, in `ast/models.py` — so
   the typed-handler branch in `_render_stage_list_with_coarse_blocks` can structurally never fire
   for *any* process's `BLOCK` stage, not just PID_0171's. §A5's full 3-arm dispatch template is
   unreachable code as currently gated.
2. **The new integration test encodes the implementation's own output as ground truth** rather than
   the reference file's literal text: it asserts `GOTO 'Mark Item As Exception'` (capital "As"),
   where the real deployed reference and the task prompt's own worked-example text both use
   lowercase "as". Minor on its own, but it means the "matches the worked example exactly"
   Done-when criterion is graded by a test that would pass even with this literal mismatch, and
   would not catch a regression in the label-derivation logic that continues to disagree with the
   reference casing.
3. **The synthetic unit test doesn't exercise the scenario where the real bug lives.** It defines
   only one continuation stage (an "Exception" page) — never a synthetic page with *two*
   continuation labels (an "Exception" and a "Completed" target, mirroring the real page), so it
   never asserts that a gating `IF`/skip-`GOTO` actually separates them. This exact gap is why the
   bug above shipped without being caught by either the new tests or (per point above) the prior
   review pass.
4. **Both label-name-resolution heuristics** (`"exception" in tp.name.lower()` for the dispatch
   label, and `"exception" or "completed"` for continuation-stage selection) resolve correctly for
   PID_171's actual page names by coincidence of those names, not by construction — neither ties
   back to the persisted `recover_stage_id`/Resume-target data itself. A differently-named
   continuation page, or a Block whose in-scope business logic happens to call an unrelated page
   with "completed"/"exception" in its name, would silently misroute or over-hoist. Given only
   `recover_stage_id` is persisted on the AST (confirmed in `ast/models.py` — no resume-target
   field), the "first `RESUME` after `RECOVER`" scan is a reasonable best effort with the data
   available; the separate name-substring heuristic for *which page* is the recovery destination is
   the more fragile, unvalidated part.
5. **Uncommitted.** This work sits directly in the working tree with no commit of record and no
   named author in this conversation. If accepted (in whole or after fixes), it needs a
   normal-discipline commit (scoped `git add` of `src/flowsmith/generator/pad.py` and
   `tests/generator/test_pad.py` only, conventional `type(scope): description` message, no
   author/co-author mention per `CLAUDE.md`) before being treated as done.

## Verdict

needs another implementation pass. The hard "no `IF` inside the handler" constraint is honored,
and the shallow structural Done-when assertions (one `BLOCK`, a `GOTO`, `CALL 'Mark Exception'`
outside the `BLOCK`) pass — but tracing the actual generated control flow for the one real page
this task was built around shows a genuine functional regression (every processed item gets
marked both Completed and Exception, unconditionally), because the required post-block gating `IF`
is never synthesized. That, plus typed-handler dispatch being structurally unreachable for any real
`BLOCK` stage, means §A5/§B15's core requirements are not yet met even though the narrowly-scoped
Done-when test suite currently passes.
