- **A genuine, load-bearing bug: the orchestrator's `uiFlowId` values don't match the registered
  Desktop Flow `workflow_id`s.** I built the full pipeline by hand (real PID_0171 data,
  `generate_orchestrator()` → `build_all_workflows_consolidated()`) and compared IDs directly:
  ```
  Registered desktop workflow IDs: {'DF_..._Loader': '34ED17C3-...', 'DF_..._Performer': '3B0F8A37-...'}
  Orchestrator loader uiFlowId:    662D9A36-...
  Orchestrator performer uiFlowId: AF92AC87-...
  Match loader in registered ids?    False
  Match performer in registered ids? False
  ```
  Root cause: two independent GUID-allocation code paths exist in `workflow_builder.py`.
  `generate_orchestrator()` (via `cloudflow.py`'s `_resolve_role_ids`) sources its `uiFlowId`s from
  `desktop_flow_ids()`, which reads `self._page_workflow_ids` — GUIDs minted **per individual BP
  page** by `prepare_workflow_ids()`. `build_all_workflows_consolidated()` instead mints **fresh,
  unrelated** GUIDs for the whole consolidated Loader/Performer flow via
  `allocate_consolidated_workflow_ids()`. Nothing threads one allocation into the other, so the
  orchestrator JSON — even once correctly embedded as a registered `<Workflow>` element — points
  at WorkflowIds that don't correspond to either of the 2 registered Desktop Flow elements. This is
  exactly the class of defect the reviewer methodology's well-formedness check ("no dangling
  references") exists to catch, and it directly undermines the task's stated purpose ("this task
  fixes that registration gap"). The new integration test does not catch this because it never
  cross-checks the orchestrator JSON's embedded `uiFlowId`s against the sibling desktop workflows'
  `workflow_id`s — it only asserts counts/categories/names.

## Most significant gaps

- **Orchestrator `uiFlowId` values don't match the registered Desktop Flow `workflow_id`s.**
  `generate_orchestrator()`/`_resolve_role_ids()` sources GUIDs from `desktop_flow_ids()`
  (per-*page* IDs from `prepare_workflow_ids()`); `build_all_workflows_consolidated()` mints
  entirely separate GUIDs via `allocate_consolidated_workflow_ids()` for the consolidated
  Loader/Performer flows. Nothing unifies these two ID spaces. Concretely verified with real
  PID_0171 data — 0% match rate on both Loader and Performer `uiFlowId`s. This is the single most
  important fix needed: whichever code calls `build_all_workflows_consolidated()` (this task or
  6b) must mint the consolidated role IDs *first*, feed them into `generate_orchestrator()` (or
  `cloudflow.py` must accept a `{role: id}` map keyed the same way
  `allocate_consolidated_workflow_ids()` produces), and only then build the orchestrator's
  `<Workflow>` element — not generate the orchestrator JSON from a disjoint per-page ID map.
- **Do step 2's claimed §A2 compliance check for the orchestrator template is not accurate.**
  Real, uncorrected structural gaps exist versus §A2's prose (missing per-`Try` catch scopes,
  missing the final `Respond` action, missing the nested loader-type/attended-unattended `IF`
  branches) — the template was not modified in this fix pass at all.
- **Naming is closer but not exact.** `DF_`/`CF_` prefix convention is now followed, but the exact
  strings diverge from the reference package's asymmetric naming (`..._Main` for Performer, no
  suffix for Loader).
- **The real CLI output path (`packager.py`) is unaffected and, as of Task 5a's consolidation
  change, now produces only 1 `<Workflow>` element for PID_0171** — worse than the prior review's
  ~24. This is legitimately Task 6b's scope per 6a's own "Out of scope" line, so it is not scored
  against 6a, but it's an urgent heads-up for 6b: that task's own "Do" step 1 wording ("should now
  follow Task 6a's consolidated output automatically... verify it does") is currently false and
  will need actual code changes, not just verification.
- Positive, confirmed directly: the Done-when test now exists, runs against real PID_0171 data,
  and passes; the 3 previously-dead consolidation methods now have real coverage (80% on
  `workflow_builder.py`, up from 50%); `_resolve_role_ids` now prefers structural `role` tagging
  over heuristics and that new path is actually exercised by the new test.
