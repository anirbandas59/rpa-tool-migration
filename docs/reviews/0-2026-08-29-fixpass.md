## Detailed findings

### 1. Silent friendly-name dict-key collision drops 35 real actions, including one entire category

`main()` builds `yaml_data["actions"]` as a `dict` keyed by `friendly_name` only
(`build_pad_action_index.py:1066-1088`). The real PDF legitimately reuses the same friendly name
across unrelated categories/services — e.g. "Copy file" is a distinct real action in SharePoint,
OneDrive, and OneDrive for Business, each with its own description. Because the dict has one slot
per `friendly_name` regardless of category, later entries silently overwrite earlier ones with no
warning, log line, or category-qualification in the key.

Independently reconstructed the 605-row Python source list (`ast.literal_eval` on the `PDF_ACTIONS`
literal) and diffed it against the actually-generated `pad-action-index.yaml`:

```
Azure - Virtual machines - Snapshots  orig=3  final=1   (lost 2 — overwritten by AWS - EC2 - Snapshots' "Create/Delete snapshot")
Email                                 orig=3  final=2   (lost 1)
FTP                                   orig=14 final=13  (lost 1 — "Close connection" overwritten by Active Directory's)
OneDrive for Business                 orig=21 final=0   (ENTIRE CATEGORY GONE)
SharePoint                            orig=44 final=34  (lost 10: Copy file, Copy folder, Create file, Delete file,
                                                          Get file content, Get file content using path,
                                                          Get file metadata, Get file metadata using path,
                                                          Move folder, Update file)
```

Total: 35 of 605 real, distinct PDF actions never make it into the deliverable, with zero
disclosure. This is a structural defect in the emission logic, not a transcription gap — every one
of the 27 colliding friendly-names was verified to be a *legitimate* cross-category reuse (no
same-category typo duplicates found). The fix is straightforward (key by `(category,
friendly_name)` or nest by category) but wasn't caught by the implementer's own validation, because
"YAML validation: PASS" only checks syntactic validity, and the 7-entry citation spot-check never
touched the categories that lost rows.

This directly undercuts the prior review's specific complaint about SharePoint under-coverage
("40+ actions across 3 pages... the index has only 6"): the *source transcription* now does capture
all 44 real SharePoint actions (verified against the independently re-extracted PDF text), but the
*delivered* YAML only exposes 34 of them, and OneDrive for Business — a category the prior review
also flagged as entirely missing — is fully transcribed in the script but 100% absent from the
actual file a curator would search.

### 2. 80 of 87 real dotted-syntax calls found in source files are discarded, not downgraded

The task's Do step 3 says: *"Any alignment you're not confident in gets marked `alignment:
unconfirmed` rather than silently paired wrong"* — implying uncertain matches should be retained
and flagged, not deleted. `align_pdf_to_syntax()` (lines 936-955) does the opposite for the
0.4–0.7 score band: it discovers a plausible `dotted_name`/`syntax`/`syntax_source` match, then at
lines 949-954 explicitly deletes all three fields and reports the row as indistinguishable from "no
match found at all" — description-only with no evidence a candidate ever existed. Independently
re-ran `scan_pad_sources()` the same way `main()` does (`docs/` + `samples/pad/`): it finds 1,212
raw action-call lines and 87 unique dotted action names (`Excel.LaunchExcel.*`,
`Cryptography.EncryptText.EncryptTextWithAES`, `Database.Connect`, `File.Delete`, `Folder.Delete`,
`SAP.SapLogin.SapLogInOptionSingle`, `TerminalEmulation.OpenTerminalSession.OpenSession`, etc.) — of
these, only 7 survive into the index (`grep -c "dotted_name:"` → 7). The implementer's summary
calls this "downgraded to description-only," but the code doesn't downgrade — it deletes the
evidence outright, so a curator gets no signal that e.g. `Excel.LaunchExcel.
LaunchAndOpenUnderExistingProcess` was actually found sitting in the very files scanned for "Launch
Excel." This is a real, if more defensible, deviation from the task's stated intent (better to
under-claim than mis-claim, but the task asked for *labeled uncertainty*, not *erasure*).

### 3. One of the 7 surviving "confirmed" entries is a semantic mismatch, same pattern as before

`Focus text field in window` (category "UI automation - Form filling," PDF description "Sets the
focus on a text box of a window") is marked `confirmed` with `dotted_name:
UIAutomation.FocusWindow.Focus`, citing `PID171_performer.txt:482`. Read that file directly:

```
482: UIAutomation.FocusWindow.Focus Window: appmask['Window \'SampleManager LIMS - Explorer\'']['Window \'Result Entry\'']
486: UIAutomation.FocusTextField TextField: appmask['Window \'SampleManager LIMS - Explorer\'']['Edit \'Analysis\'']
```

Line 482 (the cited line) is genuinely "focus **window**" (matches the *other* surviving entry,
"Focus window," correctly). The real "focus text field" action — `UIAutomation.FocusTextField` — is
sitting four lines below in the exact same cited file and was not picked up. This is the same
opposite-operation/wrong-target mismatch pattern the prior review flagged (e.g. `Decrease variable`
→ `IncreaseVariable`), just now occurring in 1 of 7 rather than the majority of 60. The citation
mechanism (line resolves, content matches verbatim) is sound; the *alignment* to the wrong action on
that line is not.

### 4. One fabricated/duplicated Excel entry from a column-wrap misread

`{"category": "Excel", "friendly_name": "Sort cells based on one or more columns", "description":
"Sorts cells based on one or more columns in an Excel worksheet"}` is not a real, separate PDF
action. In the source PDF (`pad_actions_v2.txt:711-750`, independently re-extracted), "Sort cells
in Excel worksheet" 's one-line description simply wraps into the next PDF column as "Sort cells
based on one or more columns in an Excel worksheet" — pdftotext's 3-column layout reflow makes this
look like a second heading if read too literally. The index carries both as if they were two
distinct actions; this is a minor, single-instance defect but indicates the same
column-wrap-misreading risk that a purely automated `pdftotext -layout` parse (which this script
still does not implement — Step 1 remains a hardcoded Python literal, same as the prior pass, just
much larger) would need to guard against systematically.

## Verdict
needs another implementation pass — specifically: (1) fix the YAML-emission key to be
`(category, friendly_name)`-qualified so cross-category same-name actions stop overwriting each
other (this alone restores 35 real actions, including a whole category); (2) retain

fields intact rather than deleting them, so the 80 additional real syntax citations sitting in the

(4) add the two missing categories (Message boxes, OneNote (Business)); (5) remove the fabricated

mechanical fixes to logic already mostly correct, and the category-breadth foundation from this
pass is solid enough to build the fix on directly rather than re-doing Step 1 from scratch.
