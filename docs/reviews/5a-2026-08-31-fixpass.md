## Verification detail

### 1. Fix 1 — CALL/FUNCTION name consistency

Confirmed in `git diff HEAD -- src/flowsmith/generator/pad.py`: `_render_page_as_function` and
`generate_page` now render `FUNCTION '{{ page.name }}' GLOBAL` using the raw page name (was
`_sanitise_filename(page.name)`), matching the `RunDesktopFlow`/`SubFlow` `CALL` renderer at
`pad.py:470` (`subflow_name=stage.name`, unchanged, always raw). This resolves the specific
space-vs-underscore mismatch the first review flagged (e.g. `Read Excel As Collection`) — verified
directly: generated Loader line 269 `CALL 'Read Excel As Collection'` now correctly matches line 89
`FUNCTION 'Read Excel As Collection' GLOBAL`.

Checked for PAD-syntax risk from using raw names (single quotes inside a page name would break the
`'...'`-quoted `FUNCTION`/`CALL` syntax): no page name in the AST or in either reference file
contains a quote character — confirmed via a scripted scan of `ast.json`'s 24 page names and the
reference files' full `FUNCTION '...'` name list. No new risk introduced by this change.

**However**, the first review's own finding #2 flagged a *second, independent* defect in the same
paragraph — `CALL 'Mark as read mail and move Exception Folder'` not matching `FUNCTION 'Mark as
read and move to exception folder'` ("different words entirely") — and this was **not
investigated or fixed**. Re-checked directly in the freshly regenerated Performer file:

```
# generated Performer line 120
CALL 'Mark as read mail and move Exception Folder'
...
# generated Performer line 1026
FUNCTION 'Mark as read and move to exception folder' GLOBAL
```

Still mismatched, verbatim, exactly as the first review found it. Two more instances of the same
class, found independently in this re-review (not previously flagged):

```
CALL 'Get Input Data from Excel'         →  no matching FUNCTION anywhere
FUNCTION 'Read Input Data From Excel' GLOBAL   (the actual page)

CALL 'ConvertConfigFile As Collection'   →  no matching FUNCTION anywhere
FUNCTION ... (page is actually named 'ConvertConfigFile As Collection - Copy', tagged loader role)
```

**Root cause, traced to source:** the AST already carries the correct resolution mechanism for
this — `stage.processid`, a "SubSheet/Process cross-reference ID from BP XML `<processid>`
element" (`ast/models.py:241`, populated by `parser/process.py:414-421`, matched against a target
page's `page_id` in three places in `ast/builder.py` — lines ~935-951, 1126-1129, 1215-1218,
explicitly built "Task 4a" for exactly this purpose). `stage.name`, by contrast, is the *calling*
ACTION stage's own developer-editable display label — BP allows this to differ freely from the
actual page it invokes. `_render_stage`'s `RunDesktopFlow`/`SubFlow` branch (`pad.py:467-471`) uses
only `stage.name`, and its signature has no access to a page-id→name map to resolve `processid`
against. This is a real, in-scope, fixable defect in the exact file/section this fix pass touched,
left unaddressed.

The implementer's summary claims Fix 1 "VERIFIED" using a single cited example
(`Read Excel As Collection`) that happens to have `stage.name == page.name` already (no
`processid`/display-name divergence in that one instance) — this is the same failure mode the
first review criticised the original implementation for (checking one example and generalising).
Across the ~17 unique non-boilerplate cross-page `CALL` targets in the regenerated Performer file,
roughly 4-5 (not counting the Fix-2-caused ones below) still dangle for this reason — a
meaningful fraction, not a single edge case.

**Separately (pre-existing, not part of Fix 1's scope, but relevant to well-formedness):** `CALL
'Get Error'` appears ~6 times in the Loader and ~40+ times in the Performer, and **no `FUNCTION
'Get Error'` is ever emitted in either generated file**. The reference files *do* define `FUNCTION
'Get Error' GLOBAL` as a synthesised boilerplate error-handling helper (confirmed:
`DF_PID_171_US_Loader.robin.txt:155`, `DF_PID_171_US_LIMS_Prelude_Main.robin.txt:219`) — this is
architecture doc §A5-A7's error-handling convention, not a real BP page (confirmed: no subsheet
named "Get Error" exists anywhere in `PID_0171.bprelease`'s 474 total subsheets across all
artefacts). The hardcoded `"Get Error"` string traces to `pad.py:627,669`, from commit `a0f3b20`,
predating this fix pass — it is not a regression this task introduced, but it is a large-scale
dangling reference present in the very output this task owns, and it wasn't mentioned in either
review's summary until now.

### 2. Fix 2 — Loader entry-point (disclosed as NOT fixed)

Confirmed via `ast.json`: Main Page (`PID_171_US_Process_LIMS_Prelude`) is `role: performer,
is_main: True`. `entry_page = next(p.is_main) or pages[0]` for the Loader role therefore falls back
to `pages[0]` of the loader-tagged pages, which is `Populate Queue`. Verified directly in the
regenerated Loader file: the main body is Acquire-Lock/Release-Lock STUB comments and
`clsEnvironmentLockingBusinessObject` boilerplate — `Populate Queue`'s actual content, not Main
Page's init/config-parse sequence (`Get User Name`, `Load Config Data`, `Get Mails`, `Populate
Queue` fused as `BLOCK`s, per architecture doc line 652's explicit mapping). This matches the
disclosure exactly.

**Two consequences beyond what the disclosure states, found in this re-review:**

**(a) The Performer's main body now contains dangling cross-role `CALL`s.** Because Main Page is
used *whole* as the Performer's entry body, and Main Page's own pre-`Get Next Item` logic calls
`Get Mails` and `Populate Queue` (both `role: loader`, absent from the Performer file), the
generated Performer file's main body opens with:

```
CALL 'Get Mails'
BLOCK 'Work'
...
CALL 'Get Input Data from Excel'
...
# TODO: WorkQueues.Get Next Item — complete this action block
...
CALL 'Populate Queue'
```

`Get Mails` and `Populate Queue` have no `FUNCTION` declaration anywhere in the Performer file —
these are new, concrete dangling references directly caused by the unresolved Fix 2 root cause,
not merely "wrong content sits in the Loader." Per architecture doc line 652, both of these are
supposed to be fused inline as `BLOCK`s *inside the Loader*, never called from the Performer at
all — the current output's cross-file `CALL`s to them don't correspond to any real construct in
the reference architecture.

**(b) Two of the Loader's own `FUNCTION` blocks are now orphaned.** `FUNCTION 'Get Mails' GLOBAL`
and `FUNCTION 'ConvertConfigFile As Collection - Copy' GLOBAL` are emitted in the Loader file, but
because the wrong page (`Populate Queue`) occupies the entry body, neither is ever called from
anywhere else in that same file (confirmed: the Loader's only real-page `CALL` is `CALL 'Read
Excel As Collection'`).

Both facts are readable directly from the same generated files the implementer inspected, and
neither is mentioned in the fix-pass summary's Fix 2 disclosure. The disclosure's own framing
("Loader's main body containing the wrong page's content") is accurate as far as it goes but
understates the defect's reach — it isn't confined to the Loader.

### 3. Fix 3 — @INPUT/@OUTPUT (disclosed as partially fixed)

`templates/pad/flow_header.robin.j2` diff confirmed: `@OUTPUT` loop added, correctly gated the
same way as `@INPUT`. `_generate_consolidated_flow` passes `input_vars=[]`, `output_vars=[]` with a
9-line source-code comment explaining the reasoning and citing this as a Task 5b/curation-workflow
item.

**Checked the "genuinely not derivable" claim directly, rather than trusting it:** Main Page's own
`Start`/`End` stage data items (the AST's only candidate for flow-level I/O) are:

```
START Start: [{'name': 'flg_SendDatatoDataGateways', ...}]
END End: []
END End7: []
```

— confirms neither `In_txt_Config` nor `Out_num_MailItemCount`/similar (the reference files' real
`@INPUT`/`@OUTPUT`) is present. Also checked the Task 3b environment-variable extraction
(`process.environment_variables`, 11 entries) as an alternative source the implementer might have
missed: none of the 11 names correspond to the reference's flow-level I/O either. **The technical
claim is correct — genuinely not derivable from current AST fields — and leaving the fields empty
rather than fabricating plausible-looking names is the right call** per this project's "never
invent, STOP and flag" discipline.

**But**: the generated `.robin` file itself carries **no visible indication** that `@INPUT`/
`@OUTPUT` are deliberately incomplete — the header block that used to have 46-111 spurious
`@INPUT` lines now simply has none, with no `# TODO` line in the file's own text. A downstream
consumer opening either generated `.robin` file has no way to distinguish "the tool decided this
needs manual curation" from "the tool never got around to computing this." This is a real, cheap-
to-fix gap against the project's "never silently drop a construct — leave a `# TODO` comment naming
what it was" rule (`CLAUDE.md`, `.claude/rules/pad-pipeline-workflow.md`) — the rule is followed in
the code's own comments but not carried into the artefact the rule is actually about.

## Most significant gaps

- **Fix 1 was verified against only one example and is genuinely incomplete.** A second class of
  `CALL`/`FUNCTION` dangling reference — where the calling stage's own display name (`stage.name`)
  differs from the actual target page's name, resolvable via the AST's own `stage.processid` field
  (built for exactly this in Task 4a, per `ast/builder.py`) but never consulted by
  `_render_stage`'s `RunDesktopFlow`/`SubFlow` branch — remains unaddressed. Confirmed with 3-4
  concrete, reproducible examples in the real regenerated output, one of which (`Mark as read mail
  and move Exception Folder`) is the exact case the *first* review already named.
- **Fix 2's disclosed non-fix has a bigger blast radius than stated.** Beyond the Loader carrying
  the wrong entry content, the Performer's main body (built from the same atomically-role-tagged
  Main Page) now opens with dangling `CALL`s to Loader-only pages (`Get Mails`, `Populate Queue`),
  and two of the Loader's own `FUNCTION` blocks (`Get Mails`, `ConvertConfigFile As Collection -
  Copy`) are now orphaned/never called. This is a real design-decision item (Task 4b's role-tagging
  vs. a new page-splitting capability), correctly identified as beyond this task's file scope to
  resolve alone — but the severity is high enough, and central enough to this task's stated
  purpose, that it should block a "pass" verdict on its own.
- **Fix 3's remaining gap is invisible in the actual output artefact.** The reasoning for leaving
  `@INPUT`/`@OUTPUT` empty is sound and verified correct, but no `# TODO` marker appears in the
  generated `.robin` file itself — only in a Python source comment a downstream consumer will never
  see. A one-line header comment would have closed this gap cheaply.
- **No regression test exists for `CALL`/`FUNCTION` name resolution** — the exact thing both reviews
  have now flagged twice. Without one, a third pass risks the same "fixed the cited example, missed
  the class" pattern.
- Pre-existing, out-of-5a's-scope but newly surfaced: the `CALL 'Get Error'` boilerplate
  (`pad.py:627,669`, predates this task) has no corresponding `FUNCTION 'Get Error'` emitted
  anywhere, unlike the reference files which define it as a real helper block — a large-count
  dangling reference nobody has flagged before this review.

## Verdict

needs another implementation pass — the disclosure discipline this pass showed is a real
improvement (explicit, reasoned "not fixed"/"partially fixed" framing rather than a false "all
verified" claim), and Fix 3's core judgment call (leave empty rather than fabricate) is correct.
But the task's central deliverable — that pages are consolidated into `FUNCTION`s whose `CALL`
sites actually resolve, inside a Desktop Flow body that is actually the right page's content — is
still not met: Fix 1 only closed one of two known dangling-reference classes (verified against a
single example rather than a representative sample, repeating the first review's core criticism),
and Fix 2's un-fixed entry-point selection now demonstrably corrupts both generated files, not just
the Loader. The Fix 2 root cause is legitimately a design decision beyond this task's own file
scope (Task 4b's role-tagging vs. a new page-splitting capability) and should be escalated as such
rather than forced into another 5a-scoped attempt — but Fix 1's remaining gap has no such excuse
and is squarely fixable within `generator/pad.py` using data the AST already provides.
