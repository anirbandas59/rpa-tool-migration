## Headline findings (this cycle)

**Genuinely fixed, confirmed against real output:**
- `SetVariable` wiring for `CALCULATION` stages: the fix now reads `next(iter(stage.params_map))`
  (the calc's target-variable key) instead of `stage.name`. Confirmed against the parser
  (`src/flowsmith/parser/process.py:352-355`, `params_map[calc_stage] = calc_expr`) that this key
  IS the target variable name on real data, and confirmed against `ast.json` that **104/104** real
  `CALCULATION` stages now have a non-empty `params_map` reachable by this lookup. Real output:
  277 total `SET` lines, `0` occurrences of `%SomeVar%` (was 145), e.g. `SET txt_retryCount TO
  txt_retryCount+1` (a genuine translated increment).
- `Decision` dispatch: now matches the real `target_type` template string (`"IF <expr> THEN
  <true-branch> ELSE <false-branch> END"`) instead of the non-existent `"Condition"` literal.
  Real output: **42** `IF` statements (was 0), and spot-checking several against `ast.json`'s
  `decision_expression` field confirms textually correct translation, including the exact §A7
  logic the 1st cycle called out as untranslated:
  `[Consecutive Exception Count]>=[Consecutive Exception Limit]` →
  `txt_consecutiveExceptionCount>=txt_consecutiveExceptionLimit` (line 403), and
  `Lower([Exception Type])="system exception" OR Lower([Exception Type])="internal"` →
  `Lower(txt_exceptionType)="system exception" OR Lower(txt_exceptionType)="internal"` (multiple
  occurrences, e.g. lines 211, 394, 640).
- The two new unit tests (`test_calculation_stage_with_bp_expression_translates_to_real_value`,
  `test_decision_stage_with_bp_expression_translates_to_real_value`) now correctly model the real
  parser/annotator shapes (`stage.params_map = {"txt_ExceptionType": "[Exception Type]"}` matches
  what the parser actually produces; `target_type="IF <expr> THEN..."` matches

  fixtures did — this is a real improvement in test representativeness, not just a passing count.

**Not fixed / newly surfaced, confirmed against real output:**
- **`DATA`-stage `SetVariable` wiring is still broken, by an analogous but distinct bug.**
  `_annotate_data` (`src/flowsmith/engine/annotator.py:219-253`) stores the real value in
  `annotation.params_map["initial_value"]` (a 3-key dict: `variable_name`/`variable_type`/
  `initial_value`) — but the Task 5b fix at `pad.py:1057-1091` only ever reads `stage.params_map`
  (the BP-stage-level dict, which the parser leaves empty for `DATA` stages — it's only populated
  for `Calculation`/`Action` stages). Both `CALCULATION` and `DATA` stages route through the same
  `elif ... target_type == "SetVariable"` branch, but only the `CALCULATION` half was rewired.
  Confirmed via `ast.json`: of 177 real `DATA` stages, 36 carry a real, meaningful
  `initial_value` — including `Consecutive Exception Limit` = `3`, `Consecutive Exception Count` =
  `0`, `Retry Limit` = `3`, `Retry Count` = `0` (the exact §A7 constants). None of these reach the
  generator; confirmed in real output: `SET txt_consecutiveExceptionLimit TO # TODO: No
  expression`, `SET txt_retryLimit TO # TODO: No expression` (9 occurrences of the Retry
  Limit/Count pair alone). Net effect: the `IF txt_consecutiveExceptionCount>=
  txt_consecutiveExceptionLimit THEN` line now translates *textually* correctly (see above), but
  the variable it compares against is never actually initialized to `3` anywhere in the generated
  flow — a real functional regression hiding behind a correct-looking condition.
- **§A4 prefix-by-type is implemented but wired nowhere.** `_sanitise_variable_name(item_name,

  `"text"`. Confirmed against `ast.json`: BP `number`/`flag`-typed `DATA` items whose raw name
  doesn't already carry a hand-written prefix (`Retry Limit`, `Retry Count`, `Consecutive

## Most significant gaps

- **The `DATA`-stage `SetVariable` wiring bug is the direct structural sibling of the bug this
  cycle fixed for `CALCULATION` stages, and it was missed.** Both stage types route through the
  identical `elif target_type == "SetVariable"` branch in `pad.py`, but the fix only ever consults
  `stage.params_map` (correct for `CALCULATION`, always empty for `DATA`) rather than
  `annotation.params_map` (where `_annotate_data` actually puts the real `initial_value`). This
  silently drops 36 real, business-meaningful constants including the exact §A7
  `Consecutive Exception Limit`/`Retry Limit` values the newly-fixed `IF` translation now
  correctly references but can never actually be compared against a real number.
- **Do-step 3 is still entirely unattempted, for the second consecutive cycle**, despite being
  called out by name in both the 1st cycle's review and this cycle's launch instructions. The
  Excel-template finding above shows this isn't a minor gap — without per-VBO-method template
  selection, every Excel-classified BP stage (and, by the same mechanism, every other generic
  module) collapses onto one fixed macro regardless of which real BP method was called.
- **§A4 prefix-by-type is unreachable code** — implemented, tested in isolation presumably, but
  never invoked with real type information at any of its 9 call sites in `pad.py`. This is the
  same "correct in isolation, not wired against real data" failure pattern the 1st cycle
  identified for the `SetVariable`/`Condition` dispatch bugs, recurring in a third place this
  cycle (prefix selection) after being fixed in the first two.
- **The `CreateNewDataTable` path (`COLLECTION` stages) was left completely untouched** and still
  emits invalid Robin identifiers with raw spaces — a defect from before this task even started,
  still present, still undetected by the test suite.
