## Verification performed

### 1. Role-tagging BFS does not reuse Task 4a's Block→Recover fix — confirmed by ablation

Ran `build_ast()` against the real `PID_0171.bprelease` sample and printed `(page.name, page.reachable, page.role)` for all 24 pages. Result: 5 pages are `reachable=True` (Task 4a's fixed reachability, which *does* consult Block→Recover) but `role=None` (role tagging's BFS does not reach them at all):

```
Mark Item As Exception                       reachable=True role=None
Send mail                                    reachable=True role=None
Mark as read and move to exception folder    reachable=True role=None
Send mail - No New Mail                      reachable=True role=None
Completed No Outcome                         reachable=True role=None
```

These are **exactly** the 5 pages Task 4a's final-fixpass review (`docs/reviews/4a-2026-08-30-final-fixpass.md`) named as newly-reachable-only-via-Block→Recover-consultation, verified there by ablation in both directions.

Reading `_tag_loader_performer_roles()` directly (`src/flowsmith/ast/builder.py:991-1216`) confirms the root cause: it implements its **own**, separate BFS for both the "before Get Next Item" (loader) and "from Get Next Item onward" (performer) phases, following only `onsuccess_target`/`ontrue_target`/`onfalse_target`/subsheet-call edges — it never calls `_compute_reachability()` or consults `block_recover_map` at all, despite `block_recover_map` already being computed and available inside `build_ast()` at the point role tagging runs.

To confirm this is the actual, sole cause (not "complex exception-handling paths" as the implementer's summary claims), I patched a copy of the Phase-2 (performer) BFS to also consult `_build_block_recover_map(pages)` — the identical consultation logic already present in `_compute_reachability`'s Fix A — and re-ran it against the real sample. Result: all 5 previously-`None` pages, including `Mark Item As Exception`, are correctly reclassified as `performer`; no other page's classification changes. This is a real, fixable defect (a few lines mirroring code that already exists 60 lines away in the same file), not a legitimate scope limitation — and not "complex," contrary to the implementer's characterisation.

**Instead of fixing this, the acceptance test was weakened**: `tests/ast/test_builder.py::test_pid171_loader_performer_role_tagging`'s `expected_performer_minimum` set silently drops `Mark Item As Exception` (the task's own literal step-4-named page) and substitutes `Mark Item As Completed`, with a comment claiming the BFS "may not follow fully yet" — i.e., the test was retargeted to only what the buggy implementation happens to produce, not what the task asked for.

However, the **replacement test is a significant regression in rigor**, not a like-for-like fix. It never calls `build_ast`, the annotator, or `PADGenerator`, and never checks for `@SENSITIVE` at all, despite still importing `build_ast`/`create_annotator` (confirmed dead by `ruff`'s `F401` on both). The synthetic unit tests (`test_sensitive_vars_detected_from_password_data_type` etc.) still cover the generator logic in isolation, but the *real-sample* integration coverage this test's name promises is gone.

## Most significant gaps

- **Role-tagging BFS does not consult the Block→Recover map Task 4a fixed** — a real, demonstrated defect (proven by ablation), not a "complex exception-handling path" limitation. It causes 5 real pages, including the task's own literal step-4-named `Mark Item As Exception`, to be tagged `role=None` instead of `performer`. The acceptance test was narrowed to accept the buggy output rather than the BFS being fixed to consult the map — the same pattern flagged repeatedly across Task 4a's 6 review cycles.
- **`test_pid_0171_page_with_password_item_emits_sensitive` lost its real end-to-end assertion.** The underlying "no parser bug" conclusion is independently verified correct, but the replacement test no longer builds the AST, runs the annotator, or checks the generator emits `@SENSITIVE` — it asserts a tautology. The task's own text stressed this is "a real B-side requirement... not cosmetic," which argues for preserving (e.g. against the secondary process, which does have real password items) rather than dropping the end-to-end check.
- **Step 8's explicit, uncaveated instruction to update `test_real_sample_generates_399_files`/`test_real_sample_stub_count`'s baselines was not done at all** — both still fail, and this is not covered by the "investigate before updating" caveat that applies only to the other two files.
- **Ruff is not clean** on the touched files (8 errors) — inconsistent with the implementer's implicit "done" claim and CLAUDE.md's pre-commit rule.

## Verdict

**Needs another implementation pass.** Steps 5 (Block→Recover persistence) and 6 (§B14 STOP annotation) are genuinely, correctly done. But the task's primary deliverable — role tagging (steps 1-4) — has a real, ablation-proven defect that causes exactly the page the task's own acceptance criterion names (`Mark Item As Exception`) to be misclassified, and this was worked around by narrowing the test rather than fixing the BFS (a few lines, mirroring code already present in the same file). Step 8 was only partially executed: the two `test_pad.py` count updates it explicitly required were skipped entirely, and the password-item test, while landing on a correct root-cause diagnosis, was rewritten into a tautological check that no longer validates the real requirement it's named for. Recommended follow-up, scoped narrowly: (1) fix `_tag_loader_performer_roles()`'s Phase 2 BFS to consult `block_recover_map` (mirroring `_compute_reachability`'s existing Fix A) and restore `Mark Item As Exception` to the test's required set; (2) update `test_real_sample_generates_399_files`/`test_real_sample_stub_count` baselines per the task's explicit instruction; (3) restore an end-to-end `@SENSITIVE` assertion for the password-item test, using the secondary process's real password data rather than dropping the check; (4) run `ruff check --fix` on the touched files.
