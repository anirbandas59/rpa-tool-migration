## Most significant gaps

- **Bug — `Catch:_Init`'s `Init_Flow_Exception` is wired to the wrong expression.**
  `cloudflow.py._resolve_init_email_recipient()` returns the *same* expression for both the email
  `To` field and the `Exception_Message` `SetVariable` value:
  ```python
  expr = f"@parameters('{param_key}')"
  return expr, expr   # (email_recipient_expr, failure_email_expr) — identical
  ```
  Task Do-step 1 explicitly requires `Exception_Message` to be a **coalesce of `Try:_Init`'s own
  inner action error outputs** (reference: `@coalesce(outputs('Run:_Load_Config_Data')?['body']?
  ['error']?['message'], outputs('Parse_Run:_Load_Config_result_as_JSON')?['body']?['error']?
  ['message'])`, adapted to this template's own `Compose:_Config`/`Set_Config_value` action names).
  Instead, the generated `Exception_Message` literally becomes the support-team email address
  parameter expression (verified by direct render — `@parameters('Generic_SupportTeam_EmailID
  (cr3ac_Generic_SupportTeam_EmailID)')` — or the `# TODO: ... provide recipient` placeholder text
  when no matching env var exists). That value then flows into `Terminate_Flow_-_Init`'s
  `runError.message` and `Respond_to_a_Power_App_or_flow_-_Init_fail`'s response body, so the
  init-failure notification and API response would surface an email address / TODO string instead
  of the actual initialization error. No test in `tests/generator/test_cloudflow.py` asserts
  `Init_Flow_Exception`'s value, so this shipped undetected — the 47/47 pass claim is accurate but
  doesn't cover this.
- **Missing explanatory comments on the two intentionally-empty placeholder branches.** Do-step 3
  explicitly asks for "a comment explaining this is a config-selectable path with no PAD
  implementation yet" on both `If_Loader_type_=_Cloud`'s empty true branch and
  `If_Performer_type_=_desktop`'s empty else branch (architecture doc lines 88-89, 107). JSON has
  no native comment syntax, but no Jinja2 template-source comment (`{# ... #}`) or any other
  documentation marker was added either — the empty `"actions": {}` blocks are silent, same as
  before the task.
- **`Catch:_Global_Error_Handler`'s email text was edited despite the "keep as they are today"
  instruction.** Do-step 1 says to keep `Filter_array`/`Set_Exception_Message`/
  `Get_workflow_details`/`Send_an_email_(V2)` unchanged and only add the `Respond`. The
  implementation also changed the email subject (`"- System Exception"` → `"- Global System
  Exception"`) and body (dropped the `Action: @{first(body('Filter_array'))?['name']}` line). This
