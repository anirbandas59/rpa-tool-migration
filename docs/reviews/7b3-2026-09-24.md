## (b) BP `<alwaysinit/>`-absence semantics — confirmed functionally, not independently source-cited (residual risk)

The implementer's claim that BP's runtime default when `<alwaysinit/>` is absent is "does not
reset" (persists across page runs) is **not traceable to an official Blue Prism schema/help-file
citation** — `docs/bp_schema_analysis.md` only lists the tag names (`alwaysinit`, and also a
`noalwaysinit` tag, whose semantics and even presence I could not verify: `grep -c noalwaysinit`
returns 0 across every sample currently in `samples/blueprism/`, and the file that originally
produced that schema listing, `PID_0003…xml`, is not present in the repo to re-check against). No
architecture doc, prior task, or repo file states BP's documented default before this task.

That said, the interpretation is strongly corroborated two independent ways: (1) it is the only
interpretation under which Task 7b's consecutive-exception counter — the entire reason this task
exists — can ever function, which I confirmed by hand-tracing the real rendered body per BP §A7
semantics and getting a real breach on the 4th identical message; (2) it matches the standard,
well-known Blue Prism Data-item "Always initialize this value" UI convention (checked by default
for ordinary Data items, unchecked deliberately for state that must survive across a page's
repeated calls within one process run — the classic real-world use case for exactly this kind of
counter). I could not independently verify this against an authoritative BP source in this repo,
so I flag it explicitly as a **residual, low-probability risk** rather than asserting it with full
confidence — if it is ever proven wrong, both this task and Task 7b's breach logic would need to
be re-derived.
