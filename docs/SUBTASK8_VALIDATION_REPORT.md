## 8. Divergence classification

### 8.1 CRITICAL — still unresolved

**C1 — `WorkQueues.*` actions are TODO stubs, not real PAD actions.**
Generated output contains lines such as
`# TODO: WorkQueues.Get Next Item — complete this action block`.
The reference emits real actions: `WorkQueues.GetWorkQueueItems`,
`WorkQueues.EnqueueWorkQueueItem`, `WorkQueues.UpdateWorkQueueItem`,
`WorkQueues.WorkQueueItemStatus`, `WorkQueues.ProcessWorkQueueItem`,
`WorkQueues.UpdateProcessingNotes`, `WorkQueues.WorkQueueItemPriority`.

Root cause: `mapping/vbo_catalogue.yaml` maps the Blue Prism VBO
`Blueprism.Automate.clsWorkQueuesActions` to `pa_module: WorkQueues` with
`confidence_base: 0.70`, but records **no per-method PAD action name** — the
`method_patterns` list only recognises the BP method, it does not name its PAD
counterpart. The generator therefore has nothing to emit and falls back to a stub, and
the raw BP method name leaks into the comment (`WorkQueues.Get Next Item`).

This is a **mapping-data subsystem**, not a generator bug: it needs a
`method → pa_action + parameter mapping` table per VBO method, plus a
`templates/pad/actions/work_queues.robin.j2` capable of rendering each action's
parameter list. No sub-task in the plan builds it. **Not attempted — documented only.**

**C2 — `<Claims>` are structurally correct but semantically thin.**
Generated: `selfheal`, plus `workqueues.items.get` on the 9 pages that touch WorkQueues.
Reference: 9–12 claims per flow including `workqueues.enqueue`, `workqueues.dequeue`,
`workqueues.items.update` and per-connector claims
(`connectors.execution.office365.SendEmailV2`, `connectors.swagger.sharepointonline`, …).

Claims are **not missing** — the plan's CRITICAL condition ("missing Claims") is met — but
the connector-level claims cannot be derived until C1 lands, because they are a function
of the concrete PAD action each stage resolves to. **Blocked on C1.**

### 8.2 ACCEPTABLE (explicitly sanctioned by the Sub-Task 8 mandate)

- Freshly generated GUIDs differ from the reference throughout (WorkflowId, RootComponent
  id, binary dependency GUIDs, connection-reference `padInternalId`).
- `process.environment_variables` is empty → **0** `environmentvariabledefinitions/`
  entries vs 6 in the reference. The parser does not populate environment variables yet
  (known gap carried through Sub-Tasks 1–7). Consequently the orchestrator CF JSON has
  2 `parameters` entries rather than 5.
- `Try:_Init` composes config inline rather than calling the `CF_Read_Config` child flow
  (known gap from Sub-Task 7). The reference's fourth workflow,
  `CF_PID_171_US_Read Config File`, therefore has no generated counterpart.
- The orchestrator Cloud Flow has **no `<Workflow>` element and no RootComponent** in
  `customizations.xml` — its JSON is written to `Workflows/CF_*_Cloud_Main.json` but never
  registered. Known gap from Sub-Task 7.

  **Judgement: this does *not* count as the plan's "missing Definition content" CRITICAL
  condition, but it is a genuine import-blocking gap.** A Power Platform solution only
  imports components declared in `customizations.xml`; the orchestrator JSON is inert
  payload. It is *not* a `<Definition>` problem — cloud flows legitimately carry no
  `<Definition>` (the reference's two CF workflows have none) — it is a *registration*
  problem. Registering it requires emitting a `Category=5`, no-`UIFlowType`, no-`Definition`,
  no-`Metadata` Workflow element plus its RootComponent, which is a small, well-scoped
  follow-up. It is out of Sub-Task 8's remit because Sub-Task 7 explicitly deferred it.
  **Flagged for the next sub-task.**

- `flowGeneratedBy: "Flowsmith"` vs `"PADDesigner"` — deliberate.
- `OrganizationVersion`, `<Descriptions>`, full `<Publisher>` address block — cosmetic.

### 8.3 UNKNOWN — architectural, needs a product decision

**U1 — 380 workflows vs 4.**
Flowsmith emits one desktop flow per Blue Prism page, including every page of every VBO
in the release (381 pages parsed; 380 packaged — one page is lost to a duplicate-name
`.robin` collision, see U2). The reference consolidates the entire process into
**2 desktop flows** (`DF_..._Loader`, `DF_..._LIMS_Prelude_Main`) plus **2 cloud flows**,
with BP pages becoming `FUNCTION` blocks *inside* those flows, not separate flows.

This is not a bug in any sub-task's output — it is the pipeline's current design. Closing
it means a Loader/Performer role-assignment and page-inlining pass, which needs the
`BPEdge`/call-graph system deferred through every prior sub-task. **Not attempted.**
It is also why the Category split is `6×380` rather than `5×2 + 6×2`: with no cloud-flow
*page*, `_page_runtime()` never returns `Runtime.CLOUD`, so `category=5` is never taken.
The conditional logic itself is correct and unit-tested.

**U2 — duplicate page names collide on disk.**
381 pages produce only 352 `.robin` files: 29 pages share a name with another page (e.g.
`Copy`, `Attach`, `Show`) and overwrite each other, so those workflows embed the wrong
script. Exact-stem matching (`42dd686`) removed the *wrong-file* class of this bug, but
the overwrite itself needs page-scoped filenames (`<object>_<page>.robin`), which changes
the `.robin` naming contract shared by three generators. **Not attempted — flagged.**

**U3 — unreferenced per-page Cloud Flow JSON.**
19 `*_cloudflow.json` files are copied into `Workflows/` but no Workflow element
references them. Harmless payload today; they should either be dropped or promoted to
real Workflow elements once U1 is decided.
